---
title: Neon
description: Run Social SDK inside a Neon Function next to Neon Postgres, and reconcile deliveries on a scheduled Function Trigger.
---

Neon Functions run Node.js 24, one of the SDK's tested runtimes, so the SDK runs inside the function itself. The function runs in the same region as its branch's Postgres and gets `DATABASE_URL` injected. Reconciliation runs on a scheduled Function Trigger, so you don't need an outside scheduler. Connected accounts, publication records, delivery references, and the webhook inbox live in your own Postgres tables.

## Install

```package-install
@opencoredev/social-sdk
```

The examples also use `hono`, `pg`, and `@neon/config`.

## Declare the function

Declare the function and its reconciliation schedule in `neon.ts`. The slug becomes part of the public URL and can't be changed after the first deploy.

```ts neon.ts
import { defineConfig } from "@neon/config/v1";

export default defineConfig({
  functions: {
    social: {
      name: "social publishing",
      source: "src/index.ts",
      env: {
        THREADS_USER_ID: process.env.THREADS_USER_ID!,
        THREADS_ACCESS_TOKEN: process.env.THREADS_ACCESS_TOKEN!,
      },
    },
  },
  triggers: {
    "social-reconcile": {
      type: "schedule",
      function: "social",
      cron: "*/10 * * * *",
      functionPath: "/reconcile",
    },
  },
});
```

`env` values are read when `neon deploy` evaluates the file, so load them from a local file that stays out of version control:

```bash
neon deploy --env .env.production
```

Each deployment keeps its own snapshot of these variables. Changing a token means deploying again.

## Schema

```sql
create table connected_accounts (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references tenants (id),
  platform text not null,
  account_id text not null,
  backend text not null default 'default',
  created_at timestamptz not null default now(),
  unique (tenant_id, platform, account_id)
);

create table deliveries (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references tenants (id),
  idempotency_key text not null,
  state text not null,
  delivery_ref jsonb,
  created_at timestamptz not null default now(),
  unique (tenant_id, idempotency_key)
);

create index deliveries_pending on deliveries (state)
  where state in ('processing', 'unknown');
```

Tokens do not belong in these tables. The function connects as the database owner, so every query must filter by the tenant you verified.

## Publish from the function

```ts src/index.ts
import { Hono } from "hono";
import { Pool } from "pg";
import { createSocial, connectedAccountRef } from "@opencoredev/social-sdk";
import { threads } from "@opencoredev/social-sdk/threads";

// Each isolate keeps its own pool, so total connections are max × live isolates.
const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 5 });

const social = createSocial({
  backend: threads({
    auth: {
      userId: process.env.THREADS_USER_ID!,
      accessToken: process.env.THREADS_ACCESS_TOKEN!,
    },
  }),
});

const app = new Hono();

app.post("/publish", async (c) => {
  const tenant = await requireTenant(c); // your JWT or API-key check
  const { draftId, text } = await c.req.json();

  const { rows } = await pool.query(
    "select account_id, backend from connected_accounts where tenant_id = $1 and platform = 'threads'",
    [tenant.id],
  );
  const acct = rows[0];
  if (!acct) return c.text("No authorized Threads account", 403);

  const result = await social.posts.publish({
    targets: [
      {
        account: connectedAccountRef({
          backend: acct.backend,
          platform: "threads",
          accountId: acct.account_id,
        }),
      },
    ],
    content: { text },
    idempotencyKey: draftId,
  });

  const outcome = result.outcomes[0];
  await pool.query(
    `insert into deliveries (tenant_id, idempotency_key, state, delivery_ref)
     values ($1, $2, $3, $4)
     on conflict (tenant_id, idempotency_key)
     do update set state = excluded.state, delivery_ref = excluded.delivery_ref`,
    [tenant.id, draftId, outcome?.state ?? "unknown", outcome?.delivery ?? null],
  );

  return c.json({
    status: result.status,
    outcomes: result.outcomes.map((o) => ({ state: o.state })),
  });
});

export default app;
```

A Neon Function has a public HTTPS URL that anyone can call. `requireTenant` has to reject the request before any database or SDK work: verify a JWT against your auth provider's JWKS (Neon Auth injects `NEON_AUTH_JWKS_URL` when it is enabled on the branch) or check an API key. The public URL also means browsers can call the function directly, so a long publish like a video upload doesn't hit your web host's request time limit. If you do this, handle `OPTIONS` and set CORS headers.

## Reconcile on a schedule

The trigger declared in `neon.ts` sends a `POST` to `/reconcile` every ten minutes, even when the compute has scaled to zero. The route is public, but Neon strips client-set `X-Neon-*` headers, so only trigger calls carry `X-Neon-Trigger-Invocation-Id`.

```ts
app.post("/reconcile", async (c) => {
  if (!c.req.header("x-neon-trigger-invocation-id")) return c.text("forbidden", 403);

  const { rows } = await pool.query(
    `select id, delivery_ref from deliveries
     where state in ('processing', 'unknown') and delivery_ref is not null
     limit 50`,
  );

  for (const row of rows) {
    const outcome = await social.posts.getDelivery(row.delivery_ref);
    await pool.query("update deliveries set state = $2 where id = $1", [row.id, outcome.state]);
  }

  return c.json({ checked: rows.length });
});
```

Each run reads a saved reference and writes the result, so an overlapping or redelivered run does no harm. `getDelivery` never re-sends the publish. Pick whatever cadence suits you; the SDK never polls on its own.

To test the route locally, run `neon dev` and replay the trigger call:

```bash
curl -X POST http://localhost:8787/reconcile \
  -H "X-Neon-Trigger-Invocation-Id: local-test" \
  -H "Content-Type: application/json" \
  -d '{"data":{"scheduled_at":"2026-09-22T12:00:00Z"}}'
```

## Webhooks

Hono exposes the untouched request as `c.req.raw`, which verification needs:

```ts
app.post("/events", async (c) => {
  const body = new Uint8Array(await c.req.raw.arrayBuffer());
  const verification = await adapter.webhooks?.verify(
    { headers: Object.fromEntries(c.req.raw.headers), body },
    context,
  );
  if (!verification?.valid) return c.text("unauthorized", 401);
  // decode, resolve tenants, insert into events_inbox with ON CONFLICT DO NOTHING
  return c.text("accepted", 202);
});
```

Keep the inbox in an `events_inbox` table with a unique dedupe key, following the [events guide](/events). Process pending rows from a second scheduled trigger instead of `waitUntil`: Neon documents `waitUntil` for short post-response work, and an evicted isolate drops anything still in memory.

## Notes

- Neon runs several isolates in parallel under load, and each one has its own memory. `MemoryIdempotencyStore` only covers one isolate, so implement `IdempotencyStore` (`claim` and `saveOutcome`) on Postgres and pass it to `createSocial({ idempotencyStore })`. See [idempotency](/concepts/idempotency).
- Neon can evict an isolate at any time. It sends `SIGINT`, then stops the process five seconds later. A publish interrupted this way has no saved outcome; the caller retries with the same draft ID, and the durable idempotency store keeps the retry from posting twice.
- Each branch gets its own function URL and a copy of the parent's data, including `connected_accounts`. Deploy preview branches with test credentials so a preview can't post to production accounts.
- Neon enforces a per-account limit on concurrent invocations and answers extra requests with `429` and a `Retry-After` header before your handler runs. No publish happened in that case, so the caller can retry.
- Functions are available only in some Neon regions. Check the [Neon Functions overview](https://neon.com/docs/compute/functions/overview) before creating the project.
