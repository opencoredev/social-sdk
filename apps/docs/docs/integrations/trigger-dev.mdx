description: Run scheduled social publishing and delivery reconciliation as durable Trigger.dev tasks with Social SDK idempotency keys and explicit outcomes.

Social SDK deliberately owns no scheduler: nothing in the SDK fires later, polls, or retries an uncertain public write on its own. Trigger.dev supplies that missing piece as durable tasks with retries and delays you configure, while the SDK keeps every platform call explicit.

## Install

```package-install
@opencoredev/social-sdk
```

## Share the client and stores

Task runs can land on different machines, minutes apart, so everything the SDK needs between runs must live in durable storage that every run shares:

- The client's `idempotencyStore` claims each publish before any platform call. A retried run finds that claim instead of posting twice.
- The Threads adapter's `workflowStore` holds each post between `posts.publish` and the later status reads. The default in-memory store loses it when the run's process exits.

The [Neon guide](/integrations/neon#durable-stores) has Postgres implementations of both, with their schema. Construct the client once in a module both tasks import:

```ts trigger/social.ts
import { Pool } from "pg";
import { createSocial } from "@opencoredev/social-sdk";
import { threads } from "@opencoredev/social-sdk/threads";
import { postgresIdempotencyStore, postgresThreadsWorkflowStore } from "../src/stores";

const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 5 });

export const threadsUserId = process.env.THREADS_USER_ID!;

export const social = createSocial({
  backend: threads({
    auth: { userId: threadsUserId, accessToken: process.env.THREADS_ACCESS_TOKEN! },
    workflowStore: postgresThreadsWorkflowStore(pool),
  }),
  idempotencyStore: postgresIdempotencyStore(pool),
});
```

This client holds one Threads account's token, so it can only publish as `THREADS_USER_ID`. The adapter rejects a reference to any other account, so the task checks the draft's account against it. To publish for several accounts, load each account's credentials from encrypted storage and build a client for that account.

## Scheduled publish as a task

Store the draft and its target account in your database, then let the task publish at the scheduled moment. The draft ID is the idempotency key. With the durable store, a retried run returns the first result instead of posting again.

```ts trigger/publish-scheduled.ts
import { AbortTaskRunError, task } from "@trigger.dev/sdk";
import { connectedAccountRef } from "@opencoredev/social-sdk";
import { social, threadsUserId } from "./social";

export const publishScheduled = task({
  id: "publish-scheduled-post",
  retry: { maxAttempts: 3 },
  run: async (payload: { draftId: string }) => {
    const draft = await loadDraft(payload.draftId); // your storage
    if (draft.status !== "scheduled") return { skipped: true };
    if (draft.accountId !== threadsUserId)
      throw new AbortTaskRunError("No credentials for this draft's account");

    const account = connectedAccountRef({
      backend: "default",
      platform: "threads",
      accountId: draft.accountId,
    });
    if (!(await hasActiveAccountGrant(draft.tenantId, account))) {
      await flagForReview(payload.draftId);
      throw new AbortTaskRunError("Account grant revoked");
    }

    const result = await social.posts.publish(
      {
        targets: [
          {
            account: connectedAccountRef({
              backend: "default",
              platform: "threads",
              accountId: draft.accountId,
            }),
          },
        ],
        content: { text: draft.text },
        idempotencyKey: payload.draftId,
      },
      // Scopes the idempotency key to this tenant, so tenants can't collide on a draft ID.
      { authorization: { tenantId: draft.tenantId } },
    );

    // Your storage saves complete outcomes and marks any unknown outcome for review.
    await saveOutcomes(payload.draftId, result.outcomes);
    return { status: result.status };
  },
});
```

Trigger it with a delay when the user schedules:

```ts
await publishScheduled.trigger({ draftId }, { delay: draft.publishAt });
```

For Threads, `posts.publish` stores the workflow and then makes the Threads API calls before it returns. The outcome is `published` when Threads finishes, `processing` when media is still being processed or another run holds the workflow, and `unknown` when a write may or may not have reached Threads.

:::warning
A run that returns an `unknown` outcome did not throw, so Trigger.dev does not retry it. Treat it as the end of automation: flag the draft and check the account before anything publishes again, even under a new draft ID. A run that throws or crashes is retried, and the retry finds the claim the first attempt made before dispatch. If that attempt saved its outcome, the retry returns it; if it died first, the retry returns `unknown` without calling Threads. Save outcomes inside the task before it completes. Your `saveOutcomes` implementation must atomically save the complete outcomes and move a draft with any `unknown` outcome to a review state that prevents automatic publishing.
:::

## Reconciliation as a scheduled task

Threads, Instagram, TikTok, and YouTube can return `processing`. Reconcile those deliveries on a schedule instead of polling inline:

```ts trigger/reconcile.ts
import { schedules } from "@trigger.dev/sdk";
import { social } from "./social";

export const reconcileDeliveries = schedules.task({
  id: "reconcile-deliveries",
  cron: "*/5 * * * *",
  run: async () => {
    const pending = await loadProcessingDeliveries(100); // processing, with the current draft review flag
    for (const row of pending) {
      if (row.reviewRequired) continue;
      if (!(await hasActiveAccountGrant(row.tenantId, row.delivery))) {
        await flagDeliveryForReview(row.id);
        continue;
      }
      const outcome = await social.posts.getDelivery(row.delivery, {
        authorization: { tenantId: row.tenantId },
      });
      await saveDeliveryState(row.id, outcome.state);
    }
  },
});
```

`hasActiveAccountGrant` is your server-owned lookup of an active grant for the tenant and the reference's exact `backend`, `platform`, and `accountId`. Run it inside each task attempt before publishing or reconciling. `loadProcessingDeliveries` must join each delivery to its draft and return the current `reviewRequired` flag. Exclude review-flagged drafts from its query where possible; the loop also skips them explicitly. Restoring a grant does not clear that flag. Only an explicit review decision may make the draft eligible for automatic continuation again.

`flagForReview` and `flagDeliveryForReview` must idempotently move the associated tenant-scoped draft to review, preventing automatic publishing while preserving its saved outcome and delivery reference. This client has no `AuthorizationPolicy`; `tenantId` scopes idempotency but does not enforce a grant.

`getDelivery` is not a pure read for Threads. When a workflow is still `processing`, it claims the workflow and continues the remaining Threads calls. It never replays a workflow whose state is `unknown`; it reports `unknown` again. Leave `unknown` rows out of this query and review them instead.

## Notes

- Trigger.dev tasks run on Node, a tested SDK runtime; keep the SDK client at module scope so warm task runs reuse it. The samples import from `@trigger.dev/sdk`; the older `@trigger.dev/sdk/v3` path still works but is deprecated.
- Keep platform tokens in Trigger.dev environment variables, scoped per deployment environment.
- Task retries plus a durable SDK idempotency store are the supported pattern for at-least-once schedulers publishing at-most-once content. Trigger.dev's own `idempotencyKey` trigger option stops a duplicate trigger from starting a second run; it is separate from the SDK's claim, which protects the platform write.
