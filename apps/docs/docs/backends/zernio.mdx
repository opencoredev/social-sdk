[Zernio](https://zernio.com) is an optional managed backend. Create an account and pick a plan on [zernio.com](https://zernio.com), then create an API key in its dashboard. The key stays on the server and is passed to the adapter; connected accounts are provider records that your application must map to tenants.

```ts
import { readFile } from "node:fs/promises";
import {
  createSocial,
  connectedAccountRef,
  platformPostRef,
  type AdapterOperationContext,
  type BackendPostRef,
  type ConnectedAccountRef,
  type ConversationRef,
  type DeliveryOutcome,
  type Platform,
} from "@opencoredev/social-sdk";
import { zernio } from "@opencoredev/social-sdk/cloud/zernio";

// Get tenantId from your authenticated server session and enforce account grants.
const authorization = { tenantId: "tenant-from-session" };
const social = createSocial({
  backend: zernio({
    apiKey: process.env.ZERNIO_API_KEY!,
    webhookSecret: process.env.ZERNIO_WEBHOOK_SECRET!,
  }),
});
const accounts = await social.accounts.list({ backend: "default", authorization });

function selectAccount<P extends Platform>(platform: P): ConnectedAccountRef<P> {
  const match = accounts.items.find((item) => item.ref.platform === platform);
  if (!match) throw new Error(`Connect a ${platform} account first.`);
  return connectedAccountRef({
    backend: match.ref.backend,
    platform,
    accountId: match.ref.accountId,
  });
}

const account = selectAccount("x");
const youtubeAccount = selectAccount("youtube");
const instagramAccount = selectAccount("instagram");
const at = new Date(Date.now() + 7 * 86_400_000).toISOString();
const video = new Blob([await readFile("./assets/release-walkthrough.mp4")]);
```

The adapter supports account listing, publishing, external platform-feed reads and delivery status, media upload, analytics, verified webhooks, comments for X, Threads, Bluesky, YouTube, Instagram, LinkedIn, and Facebook, and messaging for X, Bluesky, Instagram, and Facebook. Provider permissions and recipient or reply-window rules still apply. Verify `X-Zernio-Signature` over the raw request bytes before decoding; accept events into a durable, tenant-resolved inbox. See [events](/events) and [capabilities](/reference/capabilities).

Run the setup on your server with your own assets and connected accounts. The later examples reuse its typed accounts, future `at`, and `authorization`. In a multi-tenant app, configure an [authorization policy](/concepts/tenant-authorization) backed by your account grants; a tenant ID alone does not enforce access. Related server helpers are in `examples/snippets/backend-zernio.ts`.

`posts.list` requests `source=external`: it reads synced platform posts and excludes posts created through Zernio. Use the stored `delivery` with `getDelivery` for backend publication status. The SDK does not expose a combined internal/external feed.

Zernio post creation sends the derived target retry key as `Idempotency-Key`, including when a retry uploads media to a different URL. This provider replay key does not bypass completed claims in a configured client idempotency store.

## Publish a video

Pass the file as a `Blob` with its MIME type and filename; the adapter uploads it to Zernio before it creates the post. Each target takes its platform's options, and images also accept `altText`.

```ts
const result = await social.posts.publish(
  {
    targets: [
      {
        account: youtubeAccount,
        options: { title: "Release walkthrough", visibility: "unlisted", madeForKids: false },
      },
      { account: instagramAccount, options: { shareToFeed: true } },
    ],
    content: {
      text: "A two-minute tour of the new release.",
      media: [
        {
          kind: "video",
          source: { kind: "blob", blob: video, fingerprint: "release-walkthrough-v1" },
          mimeType: "video/mp4",
          filename: "release-walkthrough.mp4",
        },
      ],
    },
    idempotencyKey: "release-walkthrough-v1",
  },
  { authorization: { tenantId: "tenant-from-session" } },
);
```

`result.outcomes` has one entry per target. Type each account as `ConnectedAccountRef<"youtube">` and so on so TypeScript checks the options. The adapter rejects LinkedIn `visibility: "connections"` and Threads `replyControl` at preparation.

## Schedule and check a delivery

Set `schedule.at`, with an optional IANA `timeZone`, and store the outcome's `delivery` reference. Later, read it with `getDelivery` and handle every state instead of treating the result as a boolean.

```ts
const scheduled = await social.posts.publish(
  {
    targets: [{ account }],
    content: { text: "Office hours start at 10:00." },
    schedule: { at, timeZone: "Europe/Berlin" },
  },
  { authorization },
);
const delivery = scheduled.outcomes[0]?.delivery; // store with the publication

if (!delivery) throw new Error("No delivery was confirmed; reconcile the submission first.");

// Later, for example from a job:
const outcome = await social.posts.getDelivery(delivery, { authorization });
const action = nextStep(outcome);

function nextStep(outcome: DeliveryOutcome): string {
  switch (outcome.state) {
    case "published":
      return `published ${outcome.url ?? outcome.post.postId}`;
    case "scheduled":
      return `scheduled as ${outcome.job.jobId}; check again after the scheduled time`;
    case "accepted":
    case "processing":
      return "Zernio is still working; check again later";
    case "failed":
      return outcome.retryDisposition.kind === "after-reconnect"
        ? "ask the account owner to reconnect, then publish again"
        : `failed with ${outcome.code}`;
    case "cancelled":
      return "cancelled";
    case "not-submitted":
      return `not submitted: ${outcome.reason}`;
    case "unknown":
      return "state is unclear; reconcile before retrying";
  }
}
```

## Cancel or remove a post

Cancelling works on a record with one destination whose time is still in the future. Zernio deletes the record, so the result reports `backendRecord: "deleted"`.

```ts
if (outcome.state === "scheduled") {
  const { backendRecord } = await social.posts.cancelScheduled(outcome.job, { authorization });
}
```

To take down a post that already published on X, Threads, Bluesky, YouTube, LinkedIn, or Facebook, pass the `post` from a `published` outcome. It carries the Zernio record ID that removal needs.

```ts
if (outcome.state === "published") {
  await social.posts.removeFromPlatform(outcome.post, { authorization });
}
```

`deleteBackendRecord` only deletes Zernio drafts. The SDK never creates drafts, so it applies only to drafts made in Zernio itself.

## Recover a duplicate create

A post-create HTTP 409 reports `idempotency_conflict`. When Zernio returns an existing post ID, `social.posts.publish` returns a failed outcome with an account-scoped `delivery` reference and `retryDisposition: { kind: "reconcile-first" }`. Call `social.posts.getDelivery(outcome.delivery)` before deciding whether to submit again. The status read checks for a matching destination and does not infer success from the duplicate alone. Direct adapter errors without a recovery ID retain their retry guidance. The ID identifies a backend record, not a published platform post.

If the key is still processing and Zernio supplies `Retry-After`, the error instead reports `after-delay`. If no safe recovery ID or delay is available, reconcile manually in Zernio before deciding whether to submit again. The caller owns any later attempt with the same key; the transport never replays a write. Unrecognized or oversized bodies retain the generic status error without exposing provider text or media URLs.

## Read analytics

Post metrics include impressions, reach, likes, comments, shares, saves, clicks, views, follows, and reposts where Zernio reports them. Account metrics report followers when available; followers may be omitted without the analytics add-on. Missing counters are not zero.

```ts
if (outcome.state === "published") {
  const postMetrics = await social.analytics.getPostMetrics(outcome.post, { authorization });
}
const accountMetrics = await social.analytics.getAccountMetrics(account, { authorization });
```

## Reply to comments

List comments on a published post, then reply with a comment reference built from the post and the comment `id`.

```ts
if (outcome.state !== "published") throw new Error("Wait for a confirmed platform post.");
const post = outcome.post;
const comments = await social.comments.list(post, { limit: 20, authorization });
const commentId = comments.items[0]?.["id"];

if (typeof commentId === "string") {
  await social.comments.reply(
    { ...post, kind: "comment", commentId },
    { text: "Thanks for watching." },
    { authorization },
  );
}
```

## Read and send messages

Conversation items carry an `id`. Build a conversation reference from the account and that ID to read and send messages.

```ts
const conversations = await social.messages.listConversations(account, {
  limit: 20,
  authorization,
});
const conversationId = conversations.items[0]?.["id"];

if (typeof conversationId === "string") {
  const conversation: ConversationRef = { ...account, kind: "conversation", conversationId };
  const messages = await social.messages.listMessages(conversation, { limit: 50, authorization });
  await social.messages.send(conversation, { text: "Thanks, we are on it." }, { authorization });
}
```

## Receive webhooks

Choose a strong HMAC secret, register it with the endpoint URL in Zernio webhook settings, and store the same value as `ZERNIO_WEBHOOK_SECRET` on your server. The setup passes it as `webhookSecret` to the adapter.

Read the raw bytes, verify the signature, then decode and accept the event. Only the verify call sits inside the `try`, so a decoding or inbox failure is not reported as an authentication error.

```ts
import { SocialError } from "@opencoredev/social-sdk";
import {
  acceptWebhook,
  decodeWebhook,
  verifyZernioWebhook,
  type EventInbox,
} from "@opencoredev/social-sdk/server";

export function webhookRoute(input: {
  endpointId: string;
  inbox: EventInbox;
  resolveTenants: (backend: string, accountIds: readonly string[]) => Promise<readonly string[]>;
}) {
  return async function POST(request: Request): Promise<Response> {
    const body = new Uint8Array(await request.arrayBuffer());

    try {
      await verifyZernioWebhook({
        secret: process.env.ZERNIO_WEBHOOK_SECRET!,
        headers: request.headers,
        body,
      });
    } catch (error) {
      if (error instanceof SocialError && error.code === "unauthorized")
        return new Response("unauthorized", { status: 401 });
      throw error;
    }

    const event = await decodeWebhook({ provider: "zernio", backend: "default", body });
    const accepted = await acceptWebhook({ event, ...input });
    return new Response(accepted.state, { status: 202 });
  };
}
```

`inbox` is your durable event store and `resolveTenants` maps Zernio account IDs to your tenants. See [events](/events) for both.

## Connect accounts

The native adapter lists your Zernio profiles and starts a hosted connection flow. Native calls skip the client's authorization and concurrency checks, so run them only after your own checks.

```ts
const context: AdapterOperationContext = {
  backendInstance: "default",
  correlationId: crypto.randomUUID(),
  retryBudget: { maxAttempts: 1, maxElapsedMs: 30_000 },
  authorization: { tenantId: "tenant-from-session" },
};

const redirectUrl = "https://app.example.com/zernio/callback";
const native = social.native("default", { acknowledgeUnsafe: true });
const profiles = await native.listProfiles(context);
const profileId = profiles[0]?.["_id"];

if (typeof profileId === "string") {
  const { url } = await native.createConnection({ platform: "x", profileId, redirectUrl }, context);
}
```

A profile groups accounts; its `_id` is not a connected-account ID and cannot be used as a publish target. After the provider flow completes, list accounts again on the server, identify the newly connected account from the authorized connection session, and store its `ref.accountId`, backend and platform with that tenant's grant. Recheck the account identity before granting access. A redirect or returned URL is not tenant authorization.

Uploaded Zernio media refs expire locally after seven days. This SDK reuse limit is not a claim about the provider's public URL lifetime. Caller-owned HTTPS URLs do not receive this upload expiry. Configure `MemoryManagedMediaStore` or a persistent `ManagedMediaStore` from the backend subpath when references must survive adapter reconstruction.
