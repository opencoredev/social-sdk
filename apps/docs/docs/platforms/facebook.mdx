title: Facebook
description: Publish Facebook Page posts, Reels, and Stories with a Page access token, and manage comments, Messenger, Page settings, and Insights.
---

The direct Facebook adapter publishes to one Facebook Page through the Graph API (v27.0) with a Page access token. It covers feed posts, photos, videos, Reels, Stories, live video, native scheduling, comments, Messenger, Page management, Insights, and webhooks. Personal profiles are not supported, because Meta's API does not publish to them. To publish to Facebook through a provider-owned app instead, use a [managed backend](/backends).

For how user and Page tokens differ, how to get a long-lived Page access token, and the errors that mean the user must reconnect, read the <a href="/guides/facebook-page-access-token">Facebook Page access token guide</a>.

## Setup

<Steps>
  <Step title="Complete Meta app setup">
    Create a Meta app with Facebook Login and request `pages_show_list`, `pages_manage_posts`, and
    `pages_read_engagement`. Add `pages_manage_engagement` and `pages_read_user_content` for
    comments, `read_insights` for Page reports, `pages_messaging` for Messenger, and
    `pages_manage_metadata` for webhook subscriptions, Page settings, and Messenger conversations.
    App review and Page roles remain your setup.
  </Step>
  <Step title="Find the Page access token">
    After Facebook Login, call `discoverFacebookPages` on your server with the user access token. It
    lists every Page the user manages, with its Page access token and whether the user can perform
    `CREATE_CONTENT`, which publishing requires.
  </Step>
  <Step title="Store credentials server-side">
    Persist only the Page your application selected. Set `FACEBOOK_PAGE_ID` and
    `FACEBOOK_PAGE_ACCESS_TOKEN` in server configuration or your credential store.
  </Step>
</Steps>

```ts
import { createSocial, connectedAccountRef } from "@opencoredev/social-sdk";
import { discoverFacebookPages, facebook } from "@opencoredev/social-sdk/facebook";

// Run once after Facebook Login, on the server.
declare const userAccessToken: string;
const pages = await discoverFacebookPages({ userAccessToken });
const selected = pages.items.find((page) => page.canPublish);
if (!selected) throw new Error("The user cannot publish to any Page.");

const social = createSocial({
  backend: facebook({
    auth: {
      pageId: process.env["FACEBOOK_PAGE_ID"]!,
      accessToken: process.env["FACEBOOK_PAGE_ACCESS_TOKEN"]!,
    },
    webhookSecret: process.env["META_APP_SECRET"],
  }),
});

const account = connectedAccountRef({
  backend: "default",
  platform: "facebook",
  accountId: process.env["FACEBOOK_PAGE_ID"]!,
});
```

Page access tokens are credentials. Never log them or send them to a browser. The adapter rejects any reference whose account ID is not the configured Page.

### Facebook Login and token checks

The SDK includes server-side helpers for the Facebook Login code flow, so you do not have to hand-write these Graph calls. They are standalone functions that run on your server.

```ts
import {
  discoverFacebookPages,
  exchangeFacebookCode,
  exchangeFacebookToken,
  facebookLoginUrl,
  inspectFacebookToken,
  listFacebookPermissions,
} from "@opencoredev/social-sdk/facebook";

const app = { appId: process.env["META_APP_ID"]!, appSecret: process.env["META_APP_SECRET"]! };

// 1. Send the person to the Login dialog. Keep `state` in their server session.
const loginUrl = facebookLoginUrl({
  appId: app.appId,
  redirectUri: "https://app.example.com/facebook/callback",
  state: crypto.randomUUID(),
  scopes: ["pages_show_list", "pages_manage_posts", "pages_read_engagement"],
});

// 2. On the redirect, check `state`, then exchange the code and extend the token.
declare const code: string;
const short = await exchangeFacebookCode({
  ...app,
  code,
  redirectUri: "https://app.example.com/facebook/callback",
});
const long = await exchangeFacebookToken({ ...app, accessToken: short.accessToken });

// 3. Check what the person granted before listing Pages.
const { declined } = await listFacebookPermissions({ userAccessToken: long.accessToken });
const info = await inspectFacebookToken({ ...app, inputToken: long.accessToken });
const pages = await discoverFacebookPages({
  userAccessToken: long.accessToken,
  appSecret: app.appSecret,
});
```

| Helper                    | Graph call                                                    | Notes                                                                                                                                                                                                                                                                                                |
| ------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `facebookLoginUrl`        | `https://www.facebook.com/v27.0/dialog/oauth`                 | Builds the Login dialog URL with `client_id`, `redirect_uri`, `state`, `response_type=code`, and `scope`. `state` must be at least 16 characters; compare it on the redirect to stop cross-site request forgery. `rerequest: true` adds `auth_type=rerequest` to ask again for declined permissions. |
| `exchangeFacebookCode`    | `GET /oauth/access_token` with `code`                         | Exchanges the redirect's `code` for a short-lived user token. `redirectUri` must match the one sent to the dialog exactly. Returns `accessToken`, `tokenType`, and `expiresIn` seconds.                                                                                                              |
| `exchangeFacebookToken`   | `GET /oauth/access_token` with `grant_type=fb_exchange_token` | Exchanges a short-lived user token for a long-lived one (about 60 days). Page tokens that `discoverFacebookPages` reads with a long-lived user token do not expire, though Meta can still invalidate them. An expired token cannot be exchanged.                                                     |
| `inspectFacebookToken`    | `GET /debug_token`                                            | Calls with your app access token. Returns `isValid`, `issuedToThisApp` (the token's `app_id` is your app), `type`, `userId`, `scopes`, `granularScopes` (the Page IDs each `pages_*` permission covers), `expiresAt`, and `dataAccessExpiresAt`.                                                     |
| `listFacebookPermissions` | `GET /me/permissions`                                         | Splits the person's permissions into `granted`, `declined`, and `expired`, so you can explain what is missing and ask again.                                                                                                                                                                         |

The code and token exchanges send your app secret to Meta as `client_secret`, as Meta's manual login flow documents; call them only from your server. The helpers return tokens; store them like any other credential and never log them.

### appsecret_proof and rate-limit usage

```ts
const backend = facebook({
  auth: {
    pageId: process.env["FACEBOOK_PAGE_ID"]!,
    accessToken: process.env["FACEBOOK_PAGE_ACCESS_TOKEN"]!,
  },
  appSecret: process.env["META_APP_SECRET"],
  onRateLimitUsage: (usage) => {
    if ((usage.page?.callCount ?? 0) > 80) console.warn("Facebook Page usage is above 80%");
  },
});
```

With `appSecret`, every Graph call from the adapter, including Reels and video uploads on `graph-video.facebook.com`, carries `appsecret_proof`: the hex HMAC-SHA256 of the access token, keyed with the app secret. Apps that turn on Require App Secret in the app dashboard must send it, or every call fails. `discoverFacebookPages` and `listFacebookPermissions` take the same `appSecret`, and `facebookAppSecretProof(token, secret)` computes the value for your own calls. The Reels upload host (`rupload.facebook.com`) is not a Graph endpoint and gets no proof.

Meta reports how close the app is to its rate limits in response headers. With `onRateLimitUsage`, the adapter parses them after every Graph response that carries them: `X-App-Usage` (the app's platform limit) as `app`, `X-Page-Usage` (the Page token's limit) as `page`, and `X-Business-Use-Case-Usage` as `businessUseCase` rows with the `businessId`, the limit `type` (such as `pages` or `messenger`), and `estimatedTimeToRegainAccess` in minutes. `callCount`, `totalCputime`, and `totalTime` are percentages; Meta throttles at 100. The callback only observes: it does not slow requests down, and an error it throws is ignored. `parseFacebookRateLimitUsage(headers)` parses the same headers from any response.

`accounts.get` and `accounts.list` read the configured Page's `id`, `name`, and `username` and return one account record with `displayName` and `handle`. They fail as `unauthorized` if Facebook returns a different Page.

## Native calls

Facebook features outside the normalized API are native methods. Native calls bypass normalized middleware such as tenant authorization, so wrap them in your own policy. Get the typed handle with the explicit acknowledgment and pass a context whose `backendInstance` matches the account reference. The examples below use this `native` and `context`.

```ts
import type { AdapterOperationContext } from "@opencoredev/social-sdk";

const native = social.native("default", { acknowledgeUnsafe: true });
if (!native) throw new Error("Facebook native module is unavailable");

const context: AdapterOperationContext = {
  backendInstance: "default",
  correlationId: "facebook-job",
  retryBudget: { maxAttempts: 1, maxElapsedMs: 30_000 },
};
```

## Examples

### Publish a text or link post

```ts
const result = await social.posts.publish({
  targets: [{ account }],
  content: { text: "We just shipped.", link: { url: "https://example.com/changelog" } },
});
```

The outcome is `published`, and `post.postId` is the Page post ID (`{page-id}_{post-id}`). A structured `link` becomes Facebook's link preview. It is accepted on text posts only; with media, put the link in the text.

### Publish photos

One image goes to `/{page-id}/photos`. Two to ten images are uploaded as unpublished photos and attached to one feed post.

```ts
await social.posts.publish({
  targets: [{ account }],
  content: {
    text: "Launch day",
    media: [
      {
        kind: "image",
        mimeType: "image/jpeg",
        altText: "The team on stage",
        source: { kind: "https-url", url: "https://cdn.example.com/stage.jpg" },
      },
      {
        kind: "image",
        mimeType: "image/png",
        filename: "booth.png",
        source: { kind: "blob", blob: boothImage, fingerprint: "booth-v1" },
      },
    ],
  },
});
```

Media can be a public HTTPS URL or a `Blob`. Image `altText` is sent as `alt_text_custom`. If an upload fails part way through a multi-photo post, or Facebook refuses the final post, the adapter deletes the unpublished photos it uploaded. Any it could not delete are listed in the error's `details.unpublishedPhotoIds`. If the final post request ends without a definite answer, the post may exist, so its photos are kept and the target is reported as `unknown`.

### Publish a video or Reel

```ts
const video = {
  kind: "video" as const,
  mimeType: "video/mp4",
  source: { kind: "https-url" as const, url: "https://cdn.example.com/reel.mp4" },
};

const feedVideo = await social.posts.publish({
  targets: [{ account, options: { title: "Launch recap" } }],
  content: { text: "Demo", media: [video] },
});

const reel = await social.posts.publish({
  targets: [{ account, options: { reel: true, title: "Behind the scenes", isAiGenerated: false } }],
  content: { text: "Behind the scenes #studio", media: [video] },
});
```

A feed video goes to `graph-video.facebook.com/{page-id}/videos` from a hosted URL (`file_url`) or a `Blob` (`source`). The `title` option sets the video title. A `Blob` up to 1 GiB is sent in one multipart request. A larger `Blob`, or any `Blob` with `chunkedUpload: true`, goes through Meta's chunked (resumable) upload session instead of one request: `upload_phase: "start"` with `file_size` opens a session, each `transfer` sends the byte range Facebook asks for as `video_file_chunk` from `start_offset`, and `finish` publishes with the post fields. If a chunk fails after Facebook created the video, the outcome keeps the delivery reference (`unknown` or `failed` with `reconcile-first`) so you can reconcile it.

Custom thumbnails apply to Page videos only. To set a custom cover on a Page video, pass the image as a `Blob` in the attachment's `thumbnail`. It is sent as the `thumb` part, which turns the request into a multipart upload. Reels do not accept a thumbnail through this adapter.

A Reel uses Meta's three-phase Reels API (`/{page-id}/video_reels`) and needs a video that meets the Reel rows in [Media specifications](#media-specifications): either a hosted 9:16 MP4 at a public HTTPS URL or the same video as a `Blob`. A hosted video is fetched by Facebook through the `file_url` header; a `Blob` is uploaded to `rupload.facebook.com` as the request body with `offset: 0` and `file_size` headers. Videos and Reels return `processing` with a delivery reference, because Facebook processes video after upload. If a Reel upload fails after Facebook has created the Reel, the outcome still carries that delivery reference: `unknown` when the request timed out, its result is unclear, or Facebook's answer was malformed (such as an upload URL outside `rupload.facebook.com`, which is never contacted), otherwise `failed` with retry disposition `reconcile-first`. A chunked video upload whose transfer answer does not move the offset forward is `unknown` the same way. Check it with `getDelivery` before publishing again.

Reel options:

- `title` sets the Reel title, and `place` tags a location with a Page ID (find one with Pages Search). The Page must have a valid location.
- `isAiGenerated: true` sends `is_ai_generated`, Meta's disclosure that the Reel was created or edited with AI. It defaults to false.
- `draft: true` finishes the upload with `video_state: "DRAFT"`. The Reel stays unpublished, and the outcome is `accepted` with `backendState: "REEL_DRAFT"`, never `published`. A draft cannot also be scheduled.

Meta limits each Page to 30 API-published Reels in a moving 24-hour period and asks apps to enforce it, especially for scheduled Reels. The adapter counts the Reels it starts per instance and refuses the 31st within 24 hours with `rate_limited` and an `after-delay` retry disposition, before any request. It cannot see Reels that another process or person published, so keep one adapter per Page in a long-lived server or track the count yourself.

### Reel collaborators and copyright checks

```ts
const invite = await native.inviteReelCollaborator({
  account,
  videoId: "REEL_ID",
  collaboratorPageId: "PARTNER_PAGE_ID",
  context,
});

const collaborators = await native.listReelCollaborators({ account, videoId: "REEL_ID", context });
const check = await native.getReelCopyrightCheck({ account, videoId: "REEL_ID", context });
```

`inviteReelCollaborator` sends `POST /{video-id}/collaborators` with `target_id` set to the collaborator's Page ID and returns `collaboratorId` and `invitationLink`. Meta allows 10 invitations per Page per 24 hours. `listReelCollaborators` reads the same edge, where each row's `invite_status` is `Accepted`, `Declined`, or `Pending`.

`getReelCopyrightCheck` reads the Reel's `copyright_check_information`. `status` is `in_progress` until Meta finishes the check, which can take a few minutes, then `complete`; `matchesFound` says whether it found copyrighted material, and `matches` lists each match's `content_title`, `owner_copyright_policy`, and `matched_segments`. It needs `pages_read_engagement`.

### Crosspost a video

```ts
await native.crosspostVideo({
  account,
  videoId: "SOURCE_VIDEO_ID",
  description: "From our partner",
  context,
});
```

Crossposting shares a video that another Page published and allowed this Page to crosspost. It sends `crossposted_video_id` to `/{page-id}/videos`, with optional `description`, `title`, and `scheduleAt`, and returns `processing` like any Page video. The two Pages must have a crossposting relationship set up in Meta Business Suite.

### Reconcile video processing

```ts
const delivery = feedVideo.outcomes[0]?.delivery;
if (!delivery) throw new Error("Reconcile the submission before retrying.");

const outcome = await social.posts.getDelivery(delivery);
```

`getDelivery` reads the video's `status`. It returns `processing` until the publishing phase completes, then `published` with a post reference whose `native.objectType` is `"video"` once Facebook reports `publish_status: "published"`. A completed phase without that status, such as a draft, returns `unknown`. For feed and photo posts, `getDelivery` reports `published` only when `is_published` is true and `scheduled` only when the post has a publish time. An album photo's delivery ID is `photo:{photo-id}`; `getDelivery` reads the photo and reports it `published`. A failed upload, processing, or publishing phase returns `failed` with code `media_error`.

### Schedule and cancel

```ts
const scheduled = await social.posts.publish({
  targets: [{ account }],
  content: { text: "Doors open tomorrow." },
  schedule: { at: "2026-11-01T09:00:00Z" },
});

const outcome = scheduled.outcomes[0];
if (outcome?.state === "scheduled") await social.posts.cancelScheduled(outcome.job);
```

Scheduling uses Facebook's own `scheduled_publish_time`, so no job runner is required. The earliest time is 10 minutes after the request, and the latest depends on the format:

| Format                  | Latest schedule time | Source                                                                                     |
| ----------------------- | -------------------- | ------------------------------------------------------------------------------------------ |
| Text, link, photo posts | 30 days              | [Pages API posts](https://developers.facebook.com/docs/pages-api/posts)                    |
| Page videos             | 6 months             | [page/videos](https://developers.facebook.com/docs/graph-api/reference/page/videos)        |
| Reels                   | 29 days              | [Reels publishing](https://developers.facebook.com/docs/video-api/guides/reels-publishing) |

Preparation reports `facebook.schedule_window` for a time outside the window of the target's format. Meta's page/feed reference mentions 75 days for feed posts, but the Pages posts guide says 30 days, so the adapter keeps the shorter limit.

Cancelling reads the post or video first and deletes it only while Facebook reports it unpublished with a future `scheduled_publish_time`. If the item is published, its time has passed, or it has no publish time, `cancelScheduled` throws `invalid_input` and deletes nothing. A job that was due may already be live, so reconcile it with `getDelivery` instead of cancelling.

### Read and remove posts

```ts
const page = await social.posts.list(account, { limit: 25 });
const post = await social.posts.get(platformPostRef);
await social.posts.removeFromPlatform(platformPostRef);
```

`posts.list` reads `/{page-id}/posts` with Graph cursors. `posts.get` reads one post. Post rows carry `id`, `message`, `created_time`, `updated_time`, `permalink_url`, `status_type`, `is_published`, and `full_picture`, the URL of the post's largest picture. A post reference whose `native.objectType` is `"video"` reads the video fields instead, and one whose `native.objectType` is `"photo"` (an album upload) reads the Photo fields `id`, `name` (the caption), `created_time`, `updated_time`, and `link`. `removeFromPlatform` deletes the post and fails as `ambiguous_outcome` if Facebook does not confirm the deletion. Only posts the Page created can be deleted.

`posts.list` does not return Reels, because Meta's post edges omit them. List them with `native.listReels`, which reads `/{page-id}/video_reels`.

### Edit, pin, or hide a post

```ts
await native.updatePost({ account, postId: "PAGE_ID_POST_ID", message: "Updated text", context });
await native.updatePost({ account, postId: "PAGE_ID_POST_ID", pinned: true, context });
await native.updatePost({ account, postId: "PAGE_ID_POST_ID", isAiGenerated: true, context });
await native.updatePost({
  account,
  postId: "PAGE_ID_POST_ID",
  scheduleAt: "2026-12-01T09:00:00Z",
  context,
});
```

`updatePost` sends `POST /{post-id}` with any of `message`, `is_pinned`, `is_hidden`, `is_ai_generated`, and `scheduled_publish_time`. `scheduleAt` moves a scheduled, unpublished post to a new time, 10 minutes to 30 days ahead like a new schedule; a time outside that window is rejected before the request. `isAiGenerated: true` adds Meta's AI-generated label to the post, `false` removes it, and leaving it out keeps the current label; Meta added this to post edits in Graph API v27.0. Pin a post to put it at the top of the Page; hide one to remove it from the Page's timeline without deleting it. Meta lets an app edit a post's message only when that app created the post. The call fails as `ambiguous_outcome` if Facebook does not return `success: true`, so read the post before retrying.

### Scheduled, tagged, and visitor posts, and Page photos

```ts
const scheduledPosts = await native.listScheduledPosts({ account, context });
const tagged = await native.listTaggedPosts({ account, context });
const visitorPosts = await native.listVisitorPosts({ account, context });
const photos = await native.listPhotos({ account, limit: 50, context });
```

| Method               | Endpoint                          | Rows                                                                                                |
| -------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------- |
| `listScheduledPosts` | `/{page-id}/scheduled_posts`      | Scheduled posts that have not published yet, with `scheduled_publish_time` (Unix seconds).          |
| `listTaggedPosts`    | `/{page-id}/tagged`               | Tagged posts: posts by other people or Pages that tag this Page.                                    |
| `listVisitorPosts`   | `/{page-id}/visitor_posts`        | Visitor posts that people published on the Page.                                                    |
| `listReels`          | `/{page-id}/video_reels`          | The Page's Reels, with the video fields.                                                            |
| `listPhotos`         | `/{page-id}/photos?type=uploaded` | List Page photos the Page uploaded: `id`, `name` (the caption), `created_time`, `link`, `alt_text`. |

### Publish Stories

```ts
await native.publishPhotoStory({ account, photoUrl: "https://cdn.example.com/story.jpg", context });
await native.publishVideoStory({ account, videoUrl: "https://cdn.example.com/story.mp4", context });
const stories = await native.listStories({ account, status: "PUBLISHED", context });
```

A photo Story uploads the image to `/{page-id}/photos` with `published: false`, then publishes it through `/{page-id}/photo_stories` with its `photo_id`. The result is `published` with the Story's `post_id`. If Facebook refuses the Story, the adapter deletes the staged photo. The photo can be a public HTTPS URL or a `Blob`, up to 10 MB.

A video Story uses the same three phases as a Reel on `/{page-id}/video_stories`: `start`, the upload to `rupload.facebook.com` (a hosted URL or a `Blob`), and `finish`, with optional `isAiGenerated`. Stories need `pages_manage_posts`, `pages_read_engagement`, and `pages_show_list`.

### Go live

```ts
const live = await native.createLiveVideo({
  account,
  status: "LIVE_NOW",
  title: "Launch",
  context,
});
// Stream to live.secureStreamUrl with your encoder, then:
await native.endLiveVideo({ account, liveVideoId: live.id, context });
```

`createLiveVideo` creates a live video broadcast on `/{page-id}/live_videos` with `status` `UNPUBLISHED` (a preview the Page can start later) or `LIVE_NOW` (live as soon as the stream arrives), and an optional `title` (up to 254 characters) and `description`. It returns the live video `id` and `secureStreamUrl`, the RTMPS ingest URL. That URL contains the stream key, so treat it as a credential: pass it only to your encoder and never log it. The SDK does not stream video. `endLiveVideo` sends `end_live_video: true` to end the broadcast.

```ts
const planned = await native.createLiveVideo({
  account,
  status: "SCHEDULED_UNPUBLISHED",
  startAt: "2026-12-01T18:00:00Z",
  title: "Holiday launch",
  enableBackupIngest: true,
  crosspostingActions: [{ pageId: "PARTNER_PAGE_ID", action: "enable_crossposting" }],
  context,
});
await native.updateLiveVideo({
  account,
  liveVideoId: planned.id,
  status: "SCHEDULED_CANCELED",
  context,
});

const health = await native.getLiveVideo({ account, liveVideoId: live.id, context });
const poll = await native.createLivePoll({
  account,
  liveVideoId: live.id,
  question: "Which feature next?",
  options: ["Themes", "Exports"],
  context,
});
await native.updateLivePoll({ account, pollId: poll.id, action: "SHOW_VOTING", context });
```

Scheduled broadcasts use `status` `SCHEDULED_UNPUBLISHED` (a planned preview) or `SCHEDULED_LIVE` (announced to followers) with a future `startAt`, which the adapter sends as `event_params.start_time` in Unix seconds, as Meta's scheduling guide shows. The Page reads the planned time back as `planned_start_time`. `updateLiveVideo` posts to `/{live-video-id}` to change the `title`, `description`, or start time, to go live with `LIVE_NOW` (only while the encoder is sending data), or to cancel with `SCHEDULED_CANCELED`; it fails as `ambiguous_outcome` unless Meta confirms.

`createLiveVideo` also takes these broadcast options: `enableBackupIngest` (`enable_backup_ingest`, a second ingest URL for a backup encoder), `stopOnDeleteStream` (`stop_on_delete_stream`, end the broadcast when the encoder sends the RTMP deleteStream command), `contentTags` (`content_tags`), `targeting` (age and location limits, as on posts), `crosspostingActions` (`crossposting_actions`, each a `pageId` and `enable_crossposting`, `disable_crossposting`, or `enable_crossposting_and_create_post` for Pages with a crossposting relationship), and `isSpherical` with `projection` for a 360 broadcast. Broadcast `privacy` is not mapped, because the reference does not define its format for Pages.

`listLiveVideos` reads `/{page-id}/live_videos` with each broadcast's `status`, `title`, `planned_start_time`, `broadcast_start_time`, and `permalink_url`. `getLiveVideo` adds `ingest_streams` with each stream's `stream_health` (bitrates, frame rate, and resolution, refreshed every 2 seconds) and `is_master`; the adapter drops each stream's `stream_url` and `secure_stream_url`, because they contain the stream key. `deleteLiveVideo` deletes a broadcast.

Live polls: `createLivePoll` posts a `question`, at least two `options`, an optional 1-based `correctOption` for quizzes, and `showResults` to `/{live-video-id}/polls`. `updateLivePoll` posts an `action` to `/{video-poll-id}`: `SHOW_VOTING` opens voting, `SHOW_RESULTS` shows results, `CLOSE` closes the poll, `ATTACH_TO_VIDEO` attaches it, and `DELETE_POLL` deletes it. Live videos need `pages_manage_posts` and `pages_read_engagement`, a Page with at least 100 followers, and may need Meta's Live Video API feature.

### Comment natively: filters, attachments, mentions, and edits

```ts

With `summary: true`, the result also carries `totalCount`, which depends on the filter.

### Send and read Messenger messages

```ts
const conversations = await social.messages.listConversations(account, { limit: 20 });
const conversation = {
  kind: "conversation",
  version: 1,
  backend: "default",
  platform: "facebook",
  accountId: account.accountId,
  conversationId: "t_123",
} as const;
const messages = await social.messages.listMessages(conversation, { limit: 20 });
await social.messages.send(conversation, { text: "Thanks, we are on it." });

await native.sendMessage({
  account,
  recipientId: "PSID",
  messagingType: "MESSAGE_TAG",
  tag: "HUMAN_AGENT",
  attachment: { type: "image", url: "https://cdn.example.com/receipt.png", isReusable: true },
  context,
});

await native.privateReply({
  account,
  commentId: "COMMENT_ID",
  text: "We sent you the details.",
  context,
});
```

Page messaging (Messenger Platform) uses the Page access token. `messages.listConversations` reads `/{page-id}/conversations` with `platform=messenger`, returning each conversation's `id`, `updated_time`, counts, and `participants` (Page-scoped ID and name). `messages.listMessages` reads the conversation's `messages` with `id`, `message`, `created_time`, `from`, and `to`. Meta returns message details only for the 20 most recent messages of a conversation.

`messages.send` replies with `messaging_type: "RESPONSE"` to the conversation's one other participant. Meta allows a `RESPONSE` only inside the 24-hour window after the person's last message. A conversation with more or fewer participants is refused rather than guessed; use `native.sendMessage` with the recipient's Page-scoped ID instead.

`native.sendMessage` sends `POST /{page-id}/messages` with an explicit `messaging_type`:

- `RESPONSE` answers a message inside the 24-hour window.
- `UPDATE` sends a non-promotional update inside that window.
- `MESSAGE_TAG` with `tag: "HUMAN_AGENT"` lets a person on your team reply manually for up to 7 days after the person's last message. The HUMAN_AGENT tag needs Meta's Human Agent permission. Meta retired the `CONFIRMED_EVENT_UPDATE`, `ACCOUNT_UPDATE`, and `POST_PURCHASE_UPDATE` tags on April 27, 2026, so the adapter accepts only `HUMAN_AGENT`.

A message carries either `text` or one attachment. Message attachments are `image`, `video`, `audio`, or `file`, given by a public HTTPS `url` (with `isReusable: true` to have Meta keep it and return an `attachmentId`) or by a saved `attachmentId`. Generic, button, and media templates are not supported; approved utility templates go through `sendUtilityTemplate`. The result is the `messageId` and `recipientId`; a response without a message ID fails as `ambiguous_outcome`, so reconcile before sending again.

`native.privateReply` sends a private reply to the person who wrote a comment, with `recipient.comment_id`. Meta allows one private reply per comment, within 7 days of the comment; after the person answers, the normal 24-hour window applies. A Page cannot privately reply to another Page.

Messaging needs `pages_messaging`, `pages_manage_metadata`, and `pages_read_engagement`, and a Page token from someone with the `MESSAGING` task. Standard Access apps can message only people with a role on the app; Advanced Access covers everyone else.

`native.sendMessage` takes these Send API options on text and attachment messages:

| Option             | Wire field              | Notes                                                                                                                                                                                                                                |
| ------------------ | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `quickReplies`     | `message.quick_replies` | Up to 13 buttons above the composer. A `text` button has a `title` of at most 20 characters, a `payload` of at most 1,000 characters, and an optional `imageUrl`; `user_phone_number` and `user_email` ask for the person's contact. |
| `replyToMessageId` | `reply_to.mid`          | Quotes an earlier message in the conversation by its message ID.                                                                                                                                                                     |
| `notificationType` | `notification_type`     | `REGULAR` (Meta's default) plays a sound, `SILENT_PUSH` shows a notification without sound, and `NO_PUSH` sends no notification.                                                                                                     |
| `metadata`         | `message.metadata`      | Up to 1,000 characters that Meta returns in the `message_echoes` webhook, for tagging your own sends.                                                                                                                                |
| `personaId`        | `persona_id`            | Sends as a persona; without it the message uses the Page's identity.                                                                                                                                                                 |

When the person taps a text quick reply, the `messages` webhook carries the button title as text and your payload in `message.quick_reply.payload`; for `user_email` and `user_phone_number` the payload is the address or number. Read it from the decoded event's `data`.

`native.sendSenderAction` sends a `sender_action` to `POST /{page-id}/messages` with only the recipient, as Meta requires. `typing_on` and `typing_off` show or hide the typing indicator (they accept a `personaId`), and `mark_seen` marks the person's last message as seen. `react` sets an emoji `reaction` on one message by `messageId`, a repeat call changes it, and `unreact` removes it. Send typing indicators in separate requests from the message that follows. Meta answers a sender action with the recipient's ID; any other answer is `ambiguous_outcome`.

Personas let a human agent or bot speak inside the Page's conversation with their own name and picture. `native.createPersona` posts `name` (at most 50 characters) and `profile_picture_url` to `POST /{page-id}/personas`, which downloads the image (at most 8 MB). `native.listPersonas` pages through `GET /{page-id}/personas`, and `native.deletePersona` sends `DELETE /{persona-id}`. Deletion is soft: earlier messages keep the persona's name, but it cannot send new ones.

- `native.listConversations` reads `/{page-id}/conversations` (`platform=messenger`) with filters: `userId` sends `user_id` to find the conversation with one Page-scoped ID, and `folder` sends `folder` with `inbox`, `other`, `page_done` (done), or `spam`. Conversations in the requests folder that have been inactive for 30 days are not returned.
- `native.getMessage` reads one message node (`GET /{message-id}`) with its `attachments` (each with `fileUrl`, `imageData`, or `videoData`), `shares` (shared posts and Reels with `id`, `name`, `description`, `type`, and `url`), `story` (`{ id, link }` for a story reply or mention), `tags` (folder and source names such as `inbox` or `source:chat`), and `reactions` (each emoji with the IDs of the people who sent it). Messenger has no separate sticker field on the message node; an image attachment whose `image_data.render_as_sticker` is true is reported as `sticker` with its image URL. `isUnsupported` is true when the message holds content the API cannot return. Only the 20 most recent messages of a conversation can be read.

### Messenger profile, handover, and labels

```ts
import { facebookPageInboxAppId } from "@opencoredev/social-sdk/facebook";

await native.setMessengerProfile({
  account,
  getStarted: { payload: "GET_STARTED" },
  greeting: [{ locale: "default", text: "Hi {{user_first_name}}, how can we help?" }],
  iceBreakers: [
    {
      locale: "default",
      call_to_actions: [{ question: "Where is my order?", payload: "ORDER_STATUS" }],
    },
  ],
  persistentMenu: [
    {
      locale: "default",
      composer_input_disabled: false,
      call_to_actions: [{ type: "postback", title: "Talk to a person", payload: "HUMAN" }],
    },
  ],
  context,
});

await native.passThreadControl({
  account,
  recipientId: "PSID",
  targetAppId: facebookPageInboxAppId,
  metadata: "Customer asked for a person",
  context,
});

const vip = await native.createCustomLabel({ account, name: "VIP", context });
await native.setCustomLabel({ account, labelId: vip.id, userId: "PSID", assigned: true, context });
```

The Messenger profile (`/{page-id}/messenger_profile`) is the Page's welcome screen and menu. `native.setMessengerProfile` overwrites only the properties you pass: `getStarted` (`get_started`, the postback payload of the Get Started button), `greeting` (welcome text by locale, at most 160 characters each, with a `default` locale), `iceBreakers` (`ice_breakers`, up to 4 starter questions with payloads), `persistentMenu` (`persistent_menu`, the always-available menu), `whitelistedDomains` (`whitelisted_domains`, HTTPS origins for Messenger Extensions and the checkbox plugin), `accountLinkingUrl` (`account_linking_url`), and `commands`. Ice breakers, the persistent menu, and commands take Meta's own objects, such as `{ locale, call_to_actions }`. `native.getMessengerProfile` reads named properties and `native.deleteMessengerProfileFields` deletes them. Writes fail as `ambiguous_outcome` unless Meta answers `result: "success"`. Meta limits Messenger Profile calls to 10 per 10 minutes per Page. Taps on Get Started, ice breakers, and menu items arrive as `messaging_postbacks` webhooks.

The handover protocol lets two apps, or an app and Page Inbox, share one Page's conversations. One app owns a conversation at a time; the others receive its events on the `standby` channel.

| Method                 | Endpoint                                 | Notes                                                                                                                                              |
| ---------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `passThreadControl`    | `POST /{page-id}/pass_thread_control`    | Hands the conversation with `recipientId` to `targetAppId`. `facebookPageInboxAppId` (`263902037430900`) hands it to people working in Page Inbox. |
| `requestThreadControl` | `POST /{page-id}/request_thread_control` | Asks the owning app to pass control; the owner sees a `request_thread_control` event.                                                              |
| `releaseThreadControl` | `POST /{page-id}/release_thread_control` | Releases control so the conversation goes idle and any app may answer.                                                                             |
| `getThreadOwner`       | `GET /{page-id}/thread_owner`            | Returns the owning `appId`.                                                                                                                        |

Each takes optional `metadata` (at most 1,000 characters) that the other app receives. Writes fail as `ambiguous_outcome` unless Meta answers `success: true`; read the thread owner before retrying. Conversation routing is set up in the Page's settings in Meta Business Suite. `take_thread_control`, which takes a conversation without asking, is not wrapped: Meta limits it to apps it has approved for that role.

Custom labels tag people for your team and Page Inbox. `native.createCustomLabel` posts `page_label_name` to `POST /{page-id}/custom_labels`, `native.listCustomLabels` lists the Page's labels (or one person's with `userId`, `GET /{psid}/custom_labels`), `native.setCustomLabel` assigns a label (`POST /{label-id}/label` with `user`) or removes it with `assigned: false` (`DELETE /{label-id}/label`), and `native.deleteCustomLabel` deletes the label. Labels need `pages_manage_metadata` and a Page admin who accepted the Page Contact Terms; Meta cannot return labels for Messenger accounts created with a phone number.

### Utility messages and calling

```ts
const template = await native.createUtilityTemplate({
  account,
  name: "order_update",
  language: "en",
  components: [
    {
      type: "BODY",
      text: "Good news! Your order #{{1}} is on its way.",
      example: { body_text: [["566701"]] },
    },
  ],
  context,
});

await native.sendUtilityTemplate({
  account,
  recipientId: "PSID",
  name: "order_update",
  language: "en",
  body: [{ text: "566701" }],
  context,
});

await native.updateCallSettings({ account, iconEnabled: true, ringTarget: "PARTNERS", context });
```

Utility messages are approved templates for transactional updates, such as shipping, appointments, or account alerts, that you may send outside the 24-hour window. `native.createUtilityTemplate` submits a template to `POST /{page-id}/message_templates` with `category: "UTILITY"`, a `name` (lowercase letters, digits, and underscores), a `language`, and `components` (`HEADER`, `BODY`, and `BUTTONS` in Meta's shape, with example values); set `parameterFormat: "NAMED"` for `{{order_id}}`-style placeholders. Meta reviews it and returns `status` such as `PENDING` or `APPROVED`; the `messenger_template_status_update` webhook reports changes. `native.listMessageTemplates` reads the Page's templates, filtered by `name`, `status`, or `language`. `native.sendUtilityTemplate` sends an approved template with `messaging_type: "UTILITY"` and `message.template` (`name`, `language.code`, and `header` and `body` text parameters, with `parameterName` for named ones). Parameters may not contain `#`, `$`, or `%`, and utility messages must not contain marketing. All of this needs the `page_utility_messaging` permission.

The Messenger Calling API is in limited release: it works only for Pages in the countries Meta lists, after Meta enables `messenger_api_calling` for the Page. `native.getCallSettings` reads `call_hours` and `call_routing` from `GET /{page-id}/messenger_call_settings`. `native.updateCallSettings` shows or hides the call icon (`icon_enabled`), replaces weekly `call_hours` (an IANA `timezoneId` and per-day `openTime` and `closeTime` in `hhmm`; omitted days are closed), and sets inbound routing with `call_routing.ring_target` (`META` for Meta's inboxes, `PARTNERS` for apps subscribed to the calls webhook). Placing and answering calls is listed under [Not supported](#not-supported).

const postMetrics = await social.analytics.getPostMetrics(post);
const pageMetrics = await social.analytics.getAccountMetrics(account);
const report = await social.analytics.getReport(account, {
  from: "2026-10-01",

Post metrics are lifetime `reactions`, `comments`, and `shares` read from the post object (videos have no `shares`). Page metrics are `followers_count` and `fan_count`. ### Post Insights and Page Insights by period

```ts
const postInsights = await native.getPostInsights({
  account,
  postId: "PAGE_ID_POST_ID",
  metrics: ["post_media_view", "post_clicks", "post_reactions_by_type_total"],
  period: "lifetime",
  context,
});

const monthly = await native.getPageInsights({
  account,
  metrics: ["page_media_view", "page_post_engagements"],
  period: "days_28",
  datePreset: "last_28d",

```

`getPostInsights` reads Post Insights from `/{post-id}/insights` for the metric names you pass, such as `post_media_view`, `post_clicks`, `post_reactions_by_type_total`, and `post_video_views`. `getPageInsights` reads `/{page-id}/insights` with any `period` Meta defines (`day`, `week`, `days_28`, `month`, `lifetime`, or `total_over_range`) and either a `datePreset` (`last_7d`, `last_28d`, `last_90d`, `this_month`, or `maximum`) or a `since` and `until` range of at most 90 days. Each metric supports only some periods. Both return every series with its `name`, `period`, and `values`; a value is a number, or an object for metrics broken down by source or type, which the normalized `getReport` drops. They need `read_insights` and `pages_read_engagement`, and Page Insights need a Page with 100 or more likes.

### Receive webhooks

Subscribe your app to the Page's webhook fields with `native.subscribeApp({ account, fields: ["feed", "messages"], context })`, which sends `subscribed_fields` to `POST /{page-id}/subscribed_apps` and needs `pages_manage_metadata`. `native.listSubscribedApps` reads the same edge, with `cursor` and `limit`, to show which apps and fields are subscribed. To unsubscribe the app from the Page, `native.unsubscribeApp` sends `DELETE /{page-id}/subscribed_apps`; it fails as `ambiguous_outcome` unless Meta returns `success: true`. The app itself also needs the Page webhook configured in the Meta app dashboard. The adapter verifies `X-Hub-Signature-256` with your app secret and decodes `object: "page"` deliveries. Answer Meta's GET handshake with `answerMetaWebhookChallenge` from `@opencoredev/social-sdk/server`.

Subscribe to the `feed` field for posts, comments, and reactions, and to the `messages` field for Messenger, plus `message_deliveries`, `message_reads`, and `messaging_postbacks` if you need receipts and button taps. Add `messaging_handovers` and `standby` when you share the inbox with another app, and `message_edits`, `messaging_policy_enforcement`, `messaging_account_linking`, or `response_feedback` for those events. A policy enforcement event carries an `action` of `warning`, `block`, or `unblock` and a `reason`. An account linking event's `authorization_code` is redacted from `data`; read it from the raw verified body if your linking flow needs it. Decoded events map as follows:

| Delivery                                                                                              | `type`             | `originalType`                                                                                    |
| ----------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------- |
| `feed` with `item: "comment"`, `verb: "add"`                                                          | `comment.received` | `feed.comment.add`                                                                                |
| `feed` removing a status, post, photo, video, or share                                                | `post.removed`     | `feed.<item>.remove`                                                                              |
| Other `feed` changes, such as a reaction, an edited post, or a hidden comment                         | `unknown`          | `feed.<item>.<verb>`, such as `feed.reaction.add` or `feed.status.edited`                         |
| `mention` (a post or comment mentions the Page)                                                       | `unknown`          | `mention.<item>.<verb>`                                                                           |
| `ratings` (a new or changed recommendation)                                                           | `unknown`          | `ratings.<item>.<verb>`                                                                           |
| `page_change_proposal`, `page_upcoming_change`                                                        | `account.updated`  | The field name                                                                                    |
| A Messenger message                                                                                   | `message.received` | `messages` (echoes of your own messages are `message_echoes`, `unknown`)                          |
| Messenger reads, deliveries, reactions, postbacks                                                     | `unknown`          | `message_reads`, `message_deliveries`, `message_reactions`, `messaging_postbacks`                 |
| Message edits, policy enforcement, account linking, feedback                                          | `unknown`          | `message_edits`, `messaging_policy_enforcement`, `messaging_account_linking`, `response_feedback` |

The `<verb>` part is one of Meta's verbs (`add`, `edited`, `hide`, `unhide`, `remove`, and the others in the [Page webhook reference](https://developers.facebook.com/docs/graph-api/webhooks/reference/page)); an unrecognized verb leaves `originalType` as the field name. ## Raw requests

`native.request(input, context)` sends one request to a Graph API endpoint the SDK does not wrap. It sends the Page access token as a bearer token and adds `appsecret_proof` when `appSecret` is configured; on `rupload` it sends `Authorization: OAuth <token>` instead. It checks `input.account` against the configured Page and `context.backendInstance`, maps Graph error code 190 to `reconnect_required`, and reports usage headers to `onRateLimitUsage` like other calls.

Hosts: `graph` (the default) is `https://graph.facebook.com/v27.0`, `video` is `https://graph-video.facebook.com/v27.0`, and `rupload` is `https://rupload.facebook.com`. Paths on `graph` and `video` are below the pinned version. A `method` query parameter (Graph's method override, which turns a `GET` into a write) is rejected before any request; send the real HTTP method so a lost write response stays `ambiguous_outcome`.

```ts
// `native` is social.native("default", { acknowledgeUnsafe: true }); `account` is the
// connected account and `context` an AdapterOperationContext for its backend instance.
const response = await native.request(
  {
    account,
    method: "GET",
    path: `/${account.accountId}`,
    query: { fields: "fan_count,followers_count" },
    responseHeaders: ["x-business-use-case-usage"],
  },
  context,
);

if (response.responseType === "json") console.log(response.status, response.body);
```

`path` is relative to the host's base URL and starts with `/`; put parameters in `query`. Before any request, the adapter rejects absolute URLs, `//` paths, `..` segments, encoded separators, `?` or `#` in the path, and unknown host names. It also rejects credential and framing headers such as `Authorization`, `Cookie` and `Content-Type`, plus the `access_token` and `appsecret_proof` query parameters. It does not follow redirects. A body has a `kind` of `json`, `text`, `bytes`, `form` or `urlencoded`, and its kind sets `Content-Type`; `text` and `bytes` also take a `contentType`. Set `responseType` to `"text"` or `"bytes"` for a body that is not JSON. Response bodies are capped at 2 MiB, and `maxResponseBytes` raises the cap to at most 16 MiB. The result has `status`, `responseType`, `body` and lowercase `headers`. Name extra headers in `responseHeaders`; `set-cookie` is never returned. A non-2xx response rejects with a `SocialError` mapped like the adapter's other calls.

A write that also asks for `fields` uses Graph's read-after-write: Graph applies the write, then returns a standard error if the read-back fails. Such a write rejects with `ambiguous_outcome` and `reconcile-first` on any 4xx except 401, 403, 429 or error code 190, so reconcile it before you send it again.

A raw request makes one attempt. It adds no idempotency key and records no outcome, so you reconcile the writes you send. A write rejects with `ambiguous_outcome` when it fails without a definitive answer: a timeout, a cancellation after dispatch, a 5xx, or a 2xx body that cannot be decoded. Like other native calls it skips the client's tenant authorization, so check the tenant's grant for the account first. Prefer a typed method when one exists.

## Limits and requirements

- One Page per adapter instance. Create one adapter per Page and register each under its own backend key.
- An expired or revoked Page token (Graph error code 190) fails as `reconnect_required` with retry disposition `after-reconnect`.
- Replies through `posts.publish` are rejected with `reply.use_comments`; use `comments.reply`.
- Mixed image and video posts, documents, streams, per-attachment captions, and video alt text are rejected at preparation. Page videos accept custom thumbnails as a `Blob`; photos and Reels do not.

### Not supported

- Editing published posts through the normalized `posts.update` is not implemented; use `native.updatePost`.
- Other Page post update fields: Meta's [Page Post reference](https://developers.facebook.com/docs/graph-api/reference/page-post/#Updating) also lists `attached_media`, `is_published`, `place`, `backdated_time`, `feed_story_visibility`, `timeline_visibility`, and commerce fields. `updatePost` does not send them: Meta does not say whether `attached_media` replaces or adds to a post's photos, and publishing a scheduled post early or moving it in time are not wrapped beyond `scheduleAt`. Send them with `native.request` (`POST /{post-id}`) and read the post back.
- Editing a photo's caption or alt text, or creating an album: the [Photo reference](https://developers.facebook.com/docs/graph-api/reference/photo/) and the [Page albums reference](https://developers.facebook.com/docs/graph-api/reference/page/albums/) say "You can't perform this operation on this endpoint."
- Editing a Page video's title or description after upload: the current [Video reference](https://developers.facebook.com/docs/graph-api/reference/video/) documents no update parameters, so the SDK sends none. `native.request` can call `POST /{video-id}` if Meta supports it for your app.
- Messenger generic, button, and media templates are not implemented; utility templates are.
- Live Video API features beyond those listed above, such as live comments moderation and Live Online Events, are not implemented.
- Marketing messages and recurring notifications (`notification_messages_token` opt-ins): Meta deprecated Messenger marketing messages on February 10, 2026, and they are unavailable to new integrations.
- Placing, accepting, or ending Messenger calls: that flow exchanges WebRTC session descriptions in real time, which belongs in a media server rather than this SDK.
