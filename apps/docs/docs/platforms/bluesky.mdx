---
title: Bluesky
description: Publish Bluesky records and use typed AT Protocol parity operations with existing session authorization and explicit reconciliation.
---

The direct Bluesky adapter accepts an existing access JWT or a restored OAuth session, together with a DID and HTTPS service URL. It intentionally leaves user-facing OAuth to the maintained `@atproto/oauth-client-node` library. That client implements the AT Protocol requirements for PKCE, PAR, DPoP, issuer checks, token refresh, and identity verification; do not replace it with a generic code exchange.

## Setup

<Steps>
  <Step title="Choose a session source">
    For a server flow, install `@atproto/oauth-client-node@0.5.7` as an application runtime
    dependency and use `examples/snippets/bluesky-oauth.ts`. Host the client metadata and JWKS at
    the URLs named by `clientMetadata`, keep the private signing key server-side, and inject durable
    state/session stores. Read the [AT Protocol OAuth
    specification](https://atproto.com/specs/oauth) before registering metadata or callbacks.
  </Step>
  <Step title="Bind state to the tenant">
    Bind the application state supplied to `authorize` to the authenticated tenant and principal in
    durable storage, and validate that binding when the callback returns, before granting the
    session to an account. Parsing a valid OAuth callback alone does not establish tenant ownership.
  </Step>
  <Step title="Configure the adapter">
    Use `examples/snippets/bluesky-sdk-session.ts` to construct the SDK adapter from the restored
    session, or supply an access JWT directly. Never put access JWTs in browser code or public
    references.
  </Step>
</Steps>

```ts
import { createSocial, connectedAccountRef } from "@opencoredev/social-sdk";
import { bluesky } from "@opencoredev/social-sdk/bluesky";

const social = createSocial({
  backend: bluesky({
    auth: {
      service: process.env.BLUESKY_SERVICE!,
      did: process.env.BLUESKY_DID!,
      accessJwt: process.env.BLUESKY_ACCESS_JWT!,
    },
  }),
});

const account = connectedAccountRef({
  backend: "default",
  platform: "bluesky",
  accountId: process.env.BLUESKY_DID!,
});
```

When restoring an OAuth session, the adapter sends relative XRPC paths to `session.fetchHandler`, so the official client selects the verified token audience and attaches DPoP authentication. Do not extract an OAuth token into `accessJwt`.

## Examples

### Publish a text post

The adapter validates grapheme length and creates rich-text URL facets automatically.

```ts
const result = await social.posts.publish({
  targets: [{ account }],
  content: { text: "A Bluesky post with a link https://example.com" },
});
```

### Publish with images

The adapter enforces a 10 MiB image limit and a four-image maximum. HTTPS remote image hosts must pass the configured `allowMediaHost` policy. A stream is bounded while read, but the adapter needs a replayable source for retries.

```ts
const result = await social.posts.publish({
  targets: [{ account }],
  content: {
    text: "Screenshots attached",
    media: [
      { kind: "image", source: { kind: "https-url", url: "https://cdn.example.com/a.png" } },
      { kind: "image", source: { kind: "https-url", url: "https://cdn.example.com/b.png" } },
    ],
  },
});
```

### Publish a video

Video publishing follows Bluesky's documented video service flow in three explicit steps. The adapter never polls on your behalf.

1. `media.upload` sends one MP4 file to `app.bsky.video.uploadVideo` and returns a media reference. The reference's `mediaId` holds the processing job ID.
2. Your code calls `native.getVideoJobStatus` until the job reports a blob or fails. You decide the interval, the deadline, and whether to keep waiting.
3. `posts.publish` with that media reference reads the job status once. It writes an `app.bsky.embed.video` record when the blob is ready. If the job is still processing, the target fails with `media_error` and a one-second `after-delay` retry hint, and no post is created. A failed job returns `media_error` that should not be retried, with the provider's failure code in `upstreamCode`.

```ts
const adapter = bluesky({ auth: { service, did, accessJwt } });
const social = createSocial({ backend: adapter });

const video = await social.media.upload(
  {
    kind: "video",
    source: { kind: "blob", blob: file, fingerprint: "launch-clip" },
    mimeType: "video/mp4",
    filename: "launch.mp4",
  },
  account,
);

// Poll on your own schedule. Stop at your own deadline.
let job = await adapter.native!.getVideoJobStatus({ account, jobId: video.mediaId });
while (!job.blob && job.state !== "JOB_STATE_FAILED") {
  await new Promise((resolve) => setTimeout(resolve, 1500));
  job = await adapter.native!.getVideoJobStatus({ account, jobId: video.mediaId });
}

const result = await social.posts.publish({
  targets: [{ account }],
  content: {
    text: "Launch clip",
    media: [
      {
        kind: "video",
        source: { kind: "media-ref", ref: video },
        altText: "Product walkthrough",
        width: 1920,
        height: 1080,
      },
    ],
  },
});
```

A post takes exactly one video and no images. The video must be a `video/mp4` blob of at most 300,000,000 bytes, which is the `app.bsky.embed.video` lexicon limit. Other sources, such as HTTPS URLs and streams, are rejected before any request. `width` and `height` are optional but must be supplied together; they become the embed's `aspectRatio`. Captions and the `presentation` hint are not supported yet. Bluesky's own client also rejects videos longer than ten minutes. The adapter does not read video duration, so check it before uploading.

To upload, the adapter first requests a 30-minute service token from `com.atproto.server.getServiceAuth`. The token is scoped to `com.atproto.repo.uploadBlob`, and its audience is the account's PDS. The PDS DID comes from the `didDoc` that `com.atproto.server.getSession` returns. If your session does not return a DID document, set `pdsDid`, for example `did:web:pds.example.com`. `videoService` overrides the default `https://video.bsky.app` origin and must be an HTTPS origin. Job status reads carry no account credentials, and the adapter rejects any job whose DID differs from the configured account.

Accounts hosted by Bluesky need a verified email address to upload video and are subject to daily limits. `native.getVideoUploadLimits` returns `canUpload` and, when the service reports them, the remaining daily video count and byte allowance. The upload is a mutation that is never retried. A lost response is reported as `ambiguous_outcome`, so check the job or the limits before you upload again. If the service already processed the same file, it returns the existing job with its blob, and the adapter passes that job through.

### Languages and mentions

Set `options.languages` to at most three BCP 47 language tags. The adapter validates and canonicalizes them, then writes the native `langs` field. For a linked mention, supply an already-resolved DID and UTF-8 byte offsets in `options.mentions`. It performs no automatic handle lookup.

```ts
const content = { text: "🙂 @alice.example https://example.com" };
const options = {
  languages: ["en-US"],
  mentions: [{ byteStart: 5, byteEnd: 19, did: "did:plc:alice" }],
};
```

The emoji occupies four UTF-8 bytes, so the mention begins at byte five after the space. The DID must come from a trusted identity lookup; plain `@handle` text alone is not resolved into a mention. Preparation rejects split character boundaries, overlapping mention/link spans, and malformed language tags. The managed adapters reject these options because they have no verified mapping for them.

### Like a post

`adapter.native.likePost` accepts an acting account and the target post's native `{ uri, cid }`. The target may belong to another author.

```ts
import { connectedAccountRef } from "@opencoredev/social-sdk";
import { bluesky } from "@opencoredev/social-sdk/bluesky";

const adapter = bluesky({
  backend: "direct",
  auth: { service, accessJwt, did },
});

const like = await adapter.native!.likePost({
  account: connectedAccountRef({ backend: "direct", platform: "bluesky", accountId: did }),
  post: { uri: postUri, cid: postCid },
});
// Persist like.uri: unlikePost accepts only a like-record URI
// belonging to the configured DID, not the target post URI.
```

It creates an `app.bsky.feed.like` record in the acting account's repository and returns that record's URI/CID. Native calls bypass the client's tenant authorization and concurrency middleware; authorize the acting account before invoking them. Mutations use bounded transport and do not retry a lost response; reconcile uncertain acceptance before submitting again.

### Read threads natively

Bluesky replies preserve the native AT URI and CID through the adapter's native post metadata. Native reads and thread reads are available through `social.native('default', { acknowledgeUnsafe: true })`; this path bypasses normalized middleware and must be wrapped by your tenant policy.

### Search posts natively

`native.searchPosts` calls `app.bsky.feed.searchPosts`. Supply a non-empty query and, optionally,
`sort` (`latest` or `top`), `since`, `until`, `mentions`, `author`, `lang`, `domain`, `url`, and
`tags`. Pages contain provider post objects, an optional cursor, and an optional `hitsTotal`.
Bluesky documents the cursor as best effort; it may not traverse every hit. The endpoint accepts
1–100 results per request (default 25), and time bounds use ISO dates or datetimes with an
inclusive `since` and exclusive `until`.

The normalized search facade supports the provider's `recent` horizon. Bluesky does not define an
`all` horizon for this endpoint, so `scope: "all"` is rejected before a request is sent.

### Read and change relationships

The normalized graph facade maps to AT Protocol profile and graph procedures. Relationship pages use
`app.bsky.graph.getFollowers`, `getFollows`, `getBlocks`, and `getMutes`; follow and block create
repository records, while unfollow and unblock delete those records. Mute and unmute use
`muteActor` and `unmuteActor`.

```ts
const profile = await social.graph.getProfile(account, { handle: "alice.bsky.social" });
const followers = await social.graph.listRelationships(account, { kind: "followers", limit: 50 });
await social.graph.follow(profile.ref);
await social.graph.mute(profile.ref);
```

### Search actors, likes, lists, and reports

Use `native.searchActors` or `native.searchActorsTypeahead` for actor discovery. Likes use
`app.bsky.feed.getLikes` and `getActorLikes` for reads and repository records for writes. List
creation and item changes use `app.bsky.graph.list` and `listitem` records; list views and list
mutes use `app.bsky.graph.muteActorList` and `unmuteActorList`. List blocks are
`app.bsky.graph.listblock` records that the adapter creates and removes with repository procedures.
Moderation reports call `com.atproto.moderation.createReport` and require an authenticated
moderation service.

## Native operations

The typed native module covers reposts and quote posts, deletion, graph relationships,
likes, actor search, lists, moderation reports, notification reads and seen state, profile
reads/updates, feed discovery, search, `chat.bsky` conversation/message operations, and video
upload, job status, and upload limits (`uploadVideo`, `getVideoJobStatus`, and
`getVideoUploadLimits`). Chat responses remain provider-controlled moderation states; persist native
references and reconcile explicitly. Bluesky chat consent and moderation requirements still apply.

## Limits and requirements

- The adapter returns the record URI/CID as the platform reference when creation succeeds. Network failures after submission are ambiguous; reconcile before retrying.
- Published posts cannot be edited, so `posts.update` is declared `unsupported-by-platform`. `com.atproto.repo.putRecord` can rewrite an `app.bsky.feed.post` record on the PDS, but the Bluesky AppView ignores post updates ([atproto discussion #3038](https://github.com/bluesky-social/atproto/discussions/3038)). The rewrite would also produce a new CID, while replies, quotes, likes, and reposts keep strong references to the old one. The SDK does not offer that rewrite as an edit. Delete and publish again if the content must change.
- OAuth session refresh remains owned by the official session transport.
- App-password policy and application account membership remain application responsibilities.
- These are fixture-tested protocol operations; no live account verification is recorded in this repository.
