Authentication has two layers. The platform or managed provider authenticates the connection. Your application authenticates the user and decides which tenant may use that connection.

## Keep credentials server-side

Platform app secrets, OAuth client secrets, access and refresh tokens, provider API keys, and webhook secrets belong in a server-side secret store. A browser can request a connection or operation through your application, but it must not receive unrestricted credentials or native clients.

## Account lifecycle

Treat start, callback, successful connection, reconnect, unlink, disconnect, and upstream revocation as separate states. Store the backend instance, platform account identifier, tenant membership, scopes, token revision, and reconnect status in application-owned records. A display handle is not a stable authorization key.

Adapters report permission and reconnect failures as structured errors and outcomes. Everything after that is your application's action:

- **Unlink** removes one tenant's grant. Delete the grant row; other tenants and the stored token are unaffected.
- **Disconnect** removes your stored credential. The provider grant still exists, and the user can reconnect without new consent on most providers.
- **Revoke** invalidates the token at the provider. Supply a provider revocation hook to `CredentialManager` or the Web connect handlers; the SDK does not choose a revocation endpoint for you. Google, X, and TikTok document revocation endpoints: [Google](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke), [X](https://docs.x.com/resources/fundamentals/authentication/oauth-2-0/user-access-token), and [TikTok](https://developers.tiktok.com/doc/oauth-user-access-token-management). For other providers, check the provider's own documentation; some only let the user remove the app from their account settings.

See [tenant authorization](/concepts/tenant-authorization) and the [account ownership diagram](/concepts/architecture#account-connection-and-ownership) for the request boundary.

## Discover accounts before selection

Use `ConnectionManager` from `@opencoredev/social-sdk/server` with a `ConnectionStore` and the platform's OAuth provider factory. Call `begin` with the authenticated tenant and principal, requested platforms, and an exact redirect allowlist. Keep the returned attempt ID in your server session.

In the callback handler, pass the original callback URL and returned state to `discover`. The manager checks the authenticated principal, redirect, state, and expiry before claiming the code exchange. It saves the provider's account references before returning them for your account picker. Browser-supplied account identifiers do not create grants.

After the user chooses accounts, call `select` with the attempt ID, authenticated tenant and principal, and `selectedAccountIds`. Selection uses the saved discovery result and consumes the attempt together with its grants in one store transaction. `complete` combines discovery and selection for applications that already know their selected accounts.

The [integration skill](/agents/integrate-social-sdk) includes an executable handler recipe. Its provider and storage are injected by the application.

## Store contract and recovery

A production `ConnectionStore` must persist attempts and discovered accounts, atomically claim discovery, and atomically consume an attempt with all selected grants. The exchange claim must survive process restarts and must not expire automatically. `MemoryConnectionStore` implements this contract for tests, but loses state when the process exits.

Repeated callbacks can read a saved discovery result without exchanging the code again. If a code exchange is still running, or the process lost its response before saving discovery, the manager reports `reconnect_required`. Let an in-flight exchange finish or start a fresh connection. Replaying a one-use authorization code cannot safely recover missing credentials.

Connection attempts expire after ten minutes by default. Account selection must finish before expiry. The PKCE verifier stays in the store, and `begin` never returns it. `begin` returns `providerState` unless the provider's `start` result sets `providerStateSecret: true`, in which case that value also stays in the store. The Bluesky provider sets it because its provider state holds the DPoP private key. Keep them private in server storage, encrypt stored credentials separately, and use compare-and-set token revisions when refreshing.

## Durable storage

The server entry point includes SQL and Redis adapters for connection attempts and grants, credentials, refresh locks, and publication idempotency. They accept injected drivers and do not install a database client or contact a service when imported. SQL values use parameters; the SQL dialect determines placeholder syntax. Run schema initialization explicitly before serving requests.

Access-token expiry does not delete a credential record: its refresh token may still be needed. Connection grants also survive the callback attempt's expiry. Idempotency records do not expire automatically, because losing an unresolved claim would allow a retry to dispatch the same publication again. Set an application retention policy that preserves records needed for authorization and reconciliation.

The drivers persist plaintext unless you provide encryption. Connection records can contain PKCE verifiers and private provider state, so protect those records as well as credential rows. Keep SQL and Redis access restricted to your server, and use a storage namespace and credential key that isolate each tenant, principal, backend, platform, and account.

Use `createEncryptedCredentialStore` to encrypt credential values with AES-256-GCM before they reach a backing store. The application supplies encryption keys and key identifiers. Keep old keys available while records encrypted with them still exist; changing the active key affects subsequent writes. Encryption authenticates the storage key as well as the ciphertext, so moving an encrypted value to a different key fails authentication.

Encryption does not authorize a credential lookup. Check the authenticated tenant's grant before resolving a token, even when the token store is encrypted.

For example, inject a Node SQLite database and an application key resolver. `node:sqlite` needs Node.js 22.13 or later, or `--experimental-sqlite` on Node.js 22.12. A better-sqlite3 database works with the same executor, and `createPostgresExecutor` takes a `pg` client.

```ts
import type { DatabaseSync } from "node:sqlite";
import {
  createEncryptedCredentialStore,
  createSqliteExecutor,
  createSqlStores,
  DurableCredentialStore,
  parseEncryptedCredentialEnvelope,
  type EncryptedCredentialStoreOptions,
} from "@opencoredev/social-sdk/server";

async function openAuthStores(
  database: DatabaseSync,
  currentKeyId: string,
  resolveKey: EncryptedCredentialStoreOptions["resolveKey"],
) {
  const stores = createSqlStores({
    executor: createSqliteExecutor(database),
    dialect: "sqlite",
  });
  await stores.driver.createSchema();
  const envelopes = new DurableCredentialStore({
    driver: stores.driver,
    codec: {
      encode: JSON.stringify,
      decode(text) {
        const value: unknown = JSON.parse(text);
        return parseEncryptedCredentialEnvelope(value);
      },
    },
  });
  const credentials = createEncryptedCredentialStore({
    store: envelopes,
    namespace: "my-app-credentials",
    currentKeyId,
    resolveKey,
  });
  return { ...stores, credentials };
}
```

The database and key resolver must survive application restarts. This example encrypts credential values; protect the connection records separately. `createPostgresExecutor` adapts a `pg`-compatible query client, and `SqlExecutor` accepts a custom wrapper for other SQL clients. `createRedisStores` accepts a `RedisScriptRunner` whose `eval` forwards the script, key array, and argument array to your Redis client, including Upstash. Each script uses one key, which avoids cross-slot operations on Redis Cluster. Use a persistence configuration and eviction policy that retain claims and grants.

## Web OAuth routes

`createOAuthConnectHandlers` returns four handlers that each accept a Web `Request` and return a Web `Response`. Register your providers in its server-owned `connections` map, with one callback origin and path per connection.

- `begin`: POST JSON `{ connection, loginHint? }`. Returns an authorization URL and expiry, and remembers the attempt in a Secure, HttpOnly, SameSite=Lax cookie.
- `callback`: GET at the registered redirect URI, with the provider's code and state. Checks the authenticated principal and stored attempt before exchanging the code and returning discovered accounts.
- `select`: POST JSON `{ accountIds }`. Creates grants only for persisted discovered accounts, consumes the attempt, and activates the selected credentials.
- `disconnect`: POST JSON `{ grantId }`. Looks up an authorized grant through the application, calls its revocation hook, then removes the local grant and credential.

Supply `authenticate` to resolve your server session and `authorizeMutation` to validate CSRF and other mutation policy. Neither tenant nor principal comes from browser JSON. The application session cookie must survive the provider's top-level redirect. The default attempt cookie holds one active flow per browser; supply `correlation` backed by your server session when you need different tracking. Behind a proxy, derive `publicUrl` from trusted deployment configuration.

Configure the provider's credential sink to stage encrypted credentials under the attempt ID during discovery. `credentials.activate` receives the committed grants and must promote only those credentials, discard the rest, and arrange cleanup of abandoned staging records. Grant creation and credential activation are separate steps. An `activation_failed` response means grants were committed but activation needs application reconciliation or a new connection. The handlers do not replay the authorization code.

The `grants.find`, `grants.revoke`, and `grants.remove` hooks own disconnect policy. They must account for credentials shared by several grants so disconnecting one principal does not invalidate another principal's access. A failed revocation keeps local state available for retry. Every response uses `Cache-Control: no-store`, and error bodies omit provider text and connection secrets.

## Meta account callbacks

Use `createMetaDeauthorizeHandler` and `createMetaDataDeletionHandler` for Meta's form-encoded `signed_request` callbacks. These requests authenticate with the app secret, independently of browser sessions. The verifier checks HMAC-SHA256 over the original encoded payload, requires the supported algorithm and a bounded `issued_at`, and returns an app-scoped `userId` and stable `requestId`.

Map the user to your own accounts on the server. Make `onDeauthorize` and `onDataDeletion` durable and idempotent by `requestId` before resolving them. The deletion hook returns `{ statusUrl, confirmationCode }`; the route sends Meta's `{ url, confirmation_code }` response only after that hook succeeds. The HTTPS status page must distinguish accepted work from completed deletion. Deploying the routes and deleting application data remain the host application's responsibility.

## Direct OAuth providers

The server package includes direct OAuth factories for YouTube, X, TikTok, Threads, Instagram Login, LinkedIn, and Bluesky. Create them only in server code. Each factory accepts an injected `fetch` for deterministic tests, an optional `credentialSink`, and provider credentials. The `redirectUri` passed to the factory must match the exact callback URI registered with the provider and with `ConnectionManager.begin`. When one callback discovers several accounts, the sink's `save` runs once per selected account in order. If a later save fails, the earlier ones stay stored, so make `save` an idempotent upsert and let the user retry the connection.

## Complete server flow

When a provider discovers more than one account, the default credential sink receives credentials for every validated account. Pass `selectAccounts` to an OAuth factory when credentials should be persisted for only a chosen subset. The selector receives the discovered accounts and attempt and must return distinct discovered account IDs. This selection controls credential persistence; `ConnectionManager.select` still controls which discovered accounts become tenant grants.

A complete server flow looks like this:

```ts
import {
  ConnectionManager,
  MemoryConnectionStore,
  type OAuthCredentialSink,
  youtubeOAuth,
} from "@opencoredev/social-sdk/server";

const store = new MemoryConnectionStore(); // tests only; use durable storage in production
const credentialRows = new Map<string, unknown>();
const credentials: OAuthCredentialSink = {
  async save(input) {
    // Replace this map with encrypted, tenant-scoped persistence in production.
    const { tenantId, principalId, backend } = input.attempt;
    const { platform, accountId } = input.account.ref;
    const key = JSON.stringify([tenantId, principalId, backend, platform, accountId]);
    credentialRows.set(key, input.token);
  },
};
const provider = youtubeOAuth({
  clientId: process.env.GOOGLE_OAUTH_CLIENT_ID!,
  clientSecret: process.env.GOOGLE_OAUTH_CLIENT_SECRET!,
  redirectUri: "https://app.example.com/oauth/youtube/callback",
  // youtube.readonly is required: account discovery calls channels.list with mine=true.
  scopes: [
    "openid",
    "https://www.googleapis.com/auth/youtube.readonly",
    "https://www.googleapis.com/auth/youtube.upload",
  ],
  credentialSink: credentials,
});
const manager = new ConnectionManager({ store });

export async function handleConnection(input: {
  readonly tenantId: string;
  readonly principalId: string;
  readonly callbackUrl: string;
  readonly returnedState: string;
  readonly selectedAccountId: string;
}) {
  // Authenticated server request: return started.authorizationUrl to the browser.
  const started = await manager.begin({
    backend: "default", // the registry key the consuming client uses for this adapter
    tenantId: input.tenantId,
    principalId: input.principalId,
    platforms: ["youtube"],
    capabilities: ["posts.publish"],
    redirectUri: "https://app.example.com/oauth/youtube/callback",
    allowedRedirectUris: ["https://app.example.com/oauth/youtube/callback"],
    provider,
  });

  // Callback request: keep the complete callback URL and the state extracted from it.
  const discovered = await manager.discover({
    attemptId: started.attempt.id,
    tenantId: input.tenantId,
    principalId: input.principalId,
    callbackUrl: input.callbackUrl,
    returnedState: input.returnedState,
    allowedRedirectUris: ["https://app.example.com/oauth/youtube/callback"],
    provider,
  });
  // Show discovered account IDs to the authenticated user, then accept only their choice.
  const grants = await manager.select({
    attemptId: started.attempt.id,
    tenantId: input.tenantId,
    principalId: input.principalId,
    selectedAccountIds: [input.selectedAccountId],
  });
  return { started, discovered, grants };
}
```

The `backend` passed to `begin` becomes the `backend` field of every discovered account reference, and the client routes on it. Use the same key your client registers the adapter under: `createSocial({ backend })` registers a single adapter as `"default"`, and `createSocial({ backends: { youtube } })` registers it as `"youtube"`. A grant saved under any other key fails with `Unknown backend instance`.

`MemoryConnectionStore` and an in-memory credential sink are suitable for tests only. A production sink must encrypt tokens at rest, key them by tenant and principal as the example does, restrict reads to that tenant and principal, redact tokens from logs, and support atomic refresh-token rotation. The callback URL and returned state come from the provider redirect; do not accept an account ID or token from browser form data. The repository contains runnable TypeScript versions of this flow in `examples/snippets/oauth-youtube.ts` and `examples/snippets/oauth-tiktok.ts`. They use environment variables for client credentials and stop after returning the authorization URL until an application supplies a callback.

## Refresh and persist

The refresh helpers make one request and return the new token set. They do not store anything and do not run on a schedule. Your code decides when to refresh and must replace the stored credential atomically, because a provider that rotates refresh tokens invalidates the old one. Two workers refreshing the same account at once can otherwise overwrite each other.

For expiry-aware resolution, construct `CredentialManager` with a `refresh` hook and call `resolve(key)`. It refreshes when the stored access token is within `refreshSkewMs` of expiry, then returns the value and its current revision. `get(key)` remains a raw storage read. A missing expiry means the token does not expire; a malformed expiry is rejected.

The manager re-reads freshness after acquiring the shared lock. Before calling the provider, it persists a refresh marker. A timeout or uncertain response blocks another automatic refresh of that credential, including after the lock lease expires. Reconcile or save a newly authorized credential to recover. Configure `onRefreshFailure` and `onReconnectRequired` to update your application's reconnect state; callback failures do not replace the refresh result.

Manual `rotate` calls use the same marker and deadline. Custom credential codecs must preserve `refreshState`. `CredentialManager.revoke` calls your provider hook before deleting the revision it read; a replacement saved during revocation is preserved and reported as a conflict. Custom stores must implement `deleteIfRevision` to use this operation. If they do not, the manager refuses before contacting the provider.

Acquire a shared lock before reading and refreshing the credential, then save against the revision you read. `CredentialManager.rotate` does this ordering; compare-and-set alone cannot prevent two workers from sending the same rotating token to the provider.

```ts
import { CredentialManager, refreshOAuthToken } from "@opencoredev/social-sdk/server";

async function refreshStored(manager: CredentialManager, key: string) {
  return manager.rotate(key, (current) =>
    refreshOAuthToken(
      "tiktok",
      {
        clientId,
        clientSecret,
        signal: AbortSignal.timeout(15_000),
      },
      current,
    ),
  );
}
```

Construct the manager with your durable credential store and a lock shared by every worker, not a process-local memory lock. Set its lock lifetime longer than the refresh request deadline and renew or fence the lease if work can outlive it. A busy lock raises `upstream_failure` before calling the provider; reload after the active worker finishes. If persistence fails after rotation, reconcile or reconnect rather than blindly resending the old token. Encrypt stored values and use collision-free keys, such as the encoded identity tuple above.

For Bluesky, apply the same locking and revision checks to the whole `BlueskyOAuthSession`; the token-only manager does not store its DPoP key.
