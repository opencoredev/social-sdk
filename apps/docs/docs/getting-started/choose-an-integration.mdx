## Post from your own server without a SaaS

To post to social networks from your app without a hosted service in between,
use the direct route. Social SDK is an MIT-licensed TypeScript library that
runs inside your own Node.js 22.12+ or Bun server and calls each platform's API
directly: X, Bluesky, Threads, Instagram, Facebook Pages, LinkedIn, TikTok,
and YouTube. A
direct integration needs no Social SDK account, and the library sends no
telemetry.

What you run yourself:

- **Your platform apps.** Every platform except Bluesky needs a developer app
  you register, with its scopes, app review, and rate limits, and you pay any
  API charges the platform sets. Bluesky works with an app password or with
  OAuth client metadata you publish.
- **Your credential storage.** `ConnectionManager` from
  `@opencoredev/social-sdk/server` runs the OAuth flow with each platform's
  OAuth factory. You provide a `credentialSink` that encrypts token sets in
  your own database, and for Bluesky a `sessionSink` that stores the whole
  session, including its DPoP key. See [authentication](/authentication).
- **Your scheduling.** The SDK starts no background work. Call
  `social.posts.publish` from a job runner you already use.

```package-install
@opencoredev/social-sdk
```

If you'd rather run a scheduling app with its own connection screens, Postiz is
open source and can be self-hosted, and the [Postiz backend](/backends/postiz)
connects Social SDK to your instance. A self-hosted Postiz still needs your own
developer app for most networks. That adapter is available starting in 0.6.0.

## Compare the routes

The integration route owns authentication, limits, lifecycle mapping, and the network request. The platform remains the destination where an account or post exists.

| Route       | Use it when                                                                                                  | Application supplies                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Direct      | You want to call a platform API yourself and can satisfy its account, scope, review, and token requirements. | The platform application, authorization state, storage hooks where needed, and any upstream charges. |
| Zernio      | You want to use Zernio's supported connection and operation surface.                                         | A Zernio account and key, tenant mapping, and provider charges.                                      |
| Post for Me | You want to use Post for Me's supported connection and operation surface.                                    | A Post for Me account and key, tenant mapping, and provider charges.                                 |
| PostFast    | You want PostFast's connection links and scheduled posting. Every PostFast post needs a future schedule.     | A PostFast account and key, tenant mapping, and provider charges.                                    |
| Postiz      | You want Postiz Cloud or your own self-hosted Postiz to post now or on a schedule.                           | A Postiz workspace and key, tenant mapping, and plan charges or your own hosting.                    |
| Buffer      | You want Buffer to queue or publish to channels already connected in a Buffer organization.                  | A Buffer API key or OAuth token, tenant mapping, and Buffer plan limits.                             |
| Mixed       | Different accounts deliberately use different configured backends.                                           | A named backend registry and an account-to-backend assignment known before dispatch.                 |

Mixed mode does not provide failover. An X failure cannot authorize a Bluesky post, and a managed-provider failure cannot move a connected account to another provider. Account authorizations and provider records do not migrate when application code changes adapters.

To compare calling each platform's API directly with unified social media API providers, read the <a href="/guides/social-media-apis">social media APIs guide</a>. For Buffer's API keys, OAuth apps, and rate limits, read the <a href="/guides/buffer-api">Buffer API guide</a>.

Before selecting a production route, consult its capability page for the exact operation, format, runtime, permissions, account eligibility, asynchronous behavior, cost ownership, and evidence level.

The [architecture diagrams](/concepts/architecture) show how route selection and per-target outcomes stay explicit.

For server integration shapes, see the [Node, Next.js, and Hono framework recipes](/getting-started/framework-recipes).
