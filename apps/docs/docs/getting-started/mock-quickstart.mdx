To test social posting code without real API keys, give `createSocial` the `mockBackend` from `@opencoredev/social-sdk/testing` instead of a platform adapter. Your code makes the same `social.posts.publish` call it makes in production, with no credentials and no network request, and the scenario you pick decides the result: an immediate `published` outcome, media that reports `processing` until your test calls `mock.testing.advanceProcessing()`, a rate-limited `failed` outcome, or a mixed batch where every second target fails.

The deterministic testing backend is the safe first integration target. It ships with built-in accounts and webhook fixtures and takes a scenario and a fake clock, so the same input produces the same observable result in local development and CI.

```package-install
@opencoredev/social-sdk
```

Social SDK runs on Node.js 22.12 or later and on Bun. The package is ESM-only and these examples use top-level `await`, so on Node.js set `"type": "module"` in `package.json` (`npm pkg set type=module`) before you run it with `tsx`, or, in an existing CommonJS project, give the file a `.mts` extension. Without either, `tsx` fails with "Top-level await is currently not supported with the "cjs" output format". Bun runs either way. The [installation guide](/getting-started/installation) covers the runtime requirements and the `social-sdk doctor` setup check.

Save this as `quickstart.ts`, or `quickstart.mts` in an existing CommonJS project:

```ts
import { createSocial, connectedAccountRef } from "@opencoredev/social-sdk";
import { MemoryIdempotencyStore, mockBackend } from "@opencoredev/social-sdk/testing";

const mock = mockBackend({ scenario: "immediate-text-success" });
const social = createSocial({
  backend: mock,
  idempotencyStore: new MemoryIdempotencyStore(),
});

const result = await social.posts.publish({
  targets: [
    {
      account: connectedAccountRef({
        backend: "default",
        platform: "x",
        accountId: "mock-account-1",
      }),
    },
  ],
  content: { text: "Hello from the deterministic mock." },
  idempotencyKey: "docs-quickstart-1",
});

console.log(result.status, result.outcomes[0]?.state);
// complete published
```

Run it with `bun quickstart.ts`, or on Node.js with `npx tsx quickstart.ts` (`npx tsx quickstart.mts` for the `.mts` file). It runs without credentials and makes no network request. The repository keeps a tested copy in [`examples/snippets/mock-quickstart.ts`](https://github.com/opencoredev/social-sdk/blob/main/examples/snippets/mock-quickstart.ts).

## What the example proves

1. The application selects an account reference that belongs to the configured backend instance.
2. It creates one publication intent with explicit targets and content.
3. The backend returns one independent delivery outcome for each target.
4. In the `immediate-text-success` scenario that outcome is `published`, so the publication is `complete`. Other scenarios return pending states such as `processing`; the failure exercise below shows a mixed result.
5. No network request, credential lookup, timer, telemetry event, or background poll happens implicitly.

## Mock accounts

`mockBackend()` has two built-in accounts, which `social.accounts.list()` returns:

| `accountId`      | `platform` | `handle`       |
| ---------------- | ---------- | -------------- |
| `mock-account-1` | `x`        | `mock.creator` |
| `mock-account-2` | `threads`  | `mock.studio`  |

Append this to your quickstart file to print them:

```ts
const accounts = await social.accounts.list();
console.log(accounts.items.map(({ ref }) => `${ref.accountId} ${ref.platform}`));
// [ "mock-account-1 x", "mock-account-2 threads" ]
```

Publishing does not check this list. `social.posts.publish` accepts any non-empty `accountId` and `platform`, such as `bluesky` or `linkedin`, as long as the reference's `backend` names the configured backend. With this page's `createSocial({ backend: mock })` setup that name is `"default"`. Any other non-empty name makes `publish` throw an `invalid_input` error whose `issues` include `target.backend_unknown`. `social.accounts.get` finds only the two ids above, and the comment methods accept only these two `accountId` and `platform` pairs.

## Failure exercise

The `mixed-success-failure` scenario fails every second target. Publish to both mock accounts:

```ts
const mixed = createSocial({
  backend: mockBackend({ scenario: "mixed-success-failure" }),
  idempotencyStore: new MemoryIdempotencyStore(),
});

const result = await mixed.posts.publish({
  targets: [
    {
      account: connectedAccountRef({
        backend: "default",
        platform: "x",
        accountId: "mock-account-1",
      }),
    },
    {
      account: connectedAccountRef({
        backend: "default",
        platform: "threads",
        accountId: "mock-account-2",
      }),
    },
  ],
  content: { text: "Hello from the deterministic mock." },
  idempotencyKey: "docs-quickstart-2",
});

console.log(
  result.status,
  result.outcomes.map((outcome) => outcome.state),
);
// partial [ "published", "failed" ]
```

Keep the successful delivery and display the failed target's `code`, `message`, and `retryDisposition`. Calling `publish` again with the same key returns these saved outcomes without dispatching. A retry of only the failed target needs a new key; see [idempotency](/concepts/idempotency) for when that is safe.

## Cleanup

Mock state is process-local. `mock.testing.reset()` clears the mock's call history and processing flag but keeps the scenario and any delivery records it created, and `MemoryIdempotencyStore.reset()` clears its claims. For full isolation, create a fresh `mockBackend` and store per test, and reset the fake clock, so outcomes do not depend on test order.
