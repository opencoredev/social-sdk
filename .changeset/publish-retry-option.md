`posts.publish` accepts an opt-in `retry: { maxAttempts, maxDelayMs?, capacityDelayMs? }` option. Within the same call, it resends only targets that were provably not posted: `failed` outcomes with `retryDisposition` `after-delay` (such as a rate limit) and `not-submitted` outcomes with reason `capacity`. It waits the requested delay, reuses the same idempotency claim and per-target key, and saves only the final outcome. `maxAttempts` is 1 through 5. A wait longer than `maxDelayMs` (default 60 seconds) is not taken. With `retry`, `retryBudget.maxElapsedMs` (default 30 seconds) is one shared deadline per target covering concurrency-queue waits and every retry; a target still queued when it passes returns `not-submitted` with reason `before-submission`, and a non-positive or non-finite value is rejected with `invalid_input` before authorization or claiming the idempotency key. `unknown` and other outcomes are never resent. Without `retry`, behavior is unchanged. The new types are `PublishOptions` and `PublishRetryPolicy`.
